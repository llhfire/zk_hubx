# 项目确认书流程 PLAN

> 状态：已 grill 并锁定，2026-09-01；本计划锁定领域边界、数据结构与实现顺序，未授权立即改业务代码。
> 事实源：`HubX/CONTEXT.md`「项目确认书」「项目确认书模板」；现有项目确认书类型、项目资料索引、项目动态投影与合同归档模型。

## 一、目标

在项目详情的“确认书”页签建立统一入口，支持阶段性成果确认和项目级通用确认，完成模板生成、我方签章、客户回签扫描件收取、管理员归档及项目/合同资料联动。

## 二、已锁定的领域决策

### 1. 实体与入口

1. 统一实体名称为“项目确认书”，分为“阶段确认书”和“通用确认书”；验收单/验收确认书仍属于最终验收类文件，不并入阶段确认书。
2. 阶段确认书当前包括原型确认书、UI 确认书、需求变更确认书，必须绑定项目、当前有效合同和具体交付阶段/节点。
3. 通用确认书用于项目暂停、恢复、延期等非阶段事项，必须绑定项目、当前有效合同、确认事由和发起人，不要求阶段节点。
4. 所有确认书从项目详情“确认书”页签发起；创建时选择大类和具体类型。该页签同时负责列表、筛选、状态跟踪和历史版本。
5. 确认书类型和模板映射由管理员配置。类型声明适用大类、字段、阶段/合同约束、启用状态和模板版本；业务人员只能选择已启用类型。

### 2. 生命周期与版本

6. 主状态：`草稿 → 我方已盖章 → 已发客户 → 客户已回签 → 已归档`，另设终态 `已作废`。
7. 项目负责人或销售在权限范围内创建/编辑草稿，并点击生成我方盖章版；不另起独立审批流。
8. 生成时按合同签约主体和模板版本填充 DOCX，记录操作人、主体、模板版本、文件版本和生成时间；生成后正文锁定，错误只能作废当前版本后重新生成。
9. 同一项目 + 合同 + 确认书类型 + 阶段节点只允许一个当前有效版本。再次发起时递增版本；新版本归档后，旧归档版本保留历史并标记“已被新版本替代”。
10. 已发客户、客户已回签和已归档状态下正文不可编辑；已归档版本不可覆盖。

### 3. 文件与回签

11. 同时保留填充后的 DOCX 源文件和叠加我司电子章的不可编辑 PDF；PDF 是发送客户与归档的正式版本，DOCX 仅作内部源文件。
12. 已发客户由项目负责人/销售手动登记，记录客户联系人或签收人、发送渠道、发送人、发送时间和发送文件版本；不接入外部电子签平台。
13. 发送时记录回签截止日期；逾期只产生“回签逾期”提醒/待办，不改变主状态；项目动态记录发送、逾期和回签事件。
14. 客户扫描件支持 PDF/JPG/PNG，多文件组成一个回签文件包并指定主文件。上传即进入“客户已回签”，保存原文件、上传人和时间。
15. 扫描件不合格不触发退回或作废流程，由有上传权限的操作人直接上传新的扫描件版本，确认书保持“客户已回签”；管理员直接判断合格后执行归档。
16. 归档必须同时存在我方带章 PDF 和客户回签文件包，并关联合同；确认书进入归档后只读。

### 4. 内容来源与关联

17. 项目、合同、客户、签约主体、负责人从项目/合同事实自动带入。阶段确认书再带入阶段/节点、成果物、版本、范围和完成情况。
18. 需求变更确认书带入变更影响、人天/工期和补充报价（如有）；补充报价与确认书不强制先后，但两者都存在时必须互相关联。
19. 通用确认书带入事由、项目状态和相关日期；草稿只允许编辑说明文字，不能修改项目、合同和阶段关联事实。
20. 需求变更确认书归档是生成补充合同的前置条件。
21. 阶段确认书归档只完成对应交付节点中的“确认书”交付物，并写入项目动态；不自动完成整个阶段。通用确认书只记录项目状态/动态；验收确认书继续走最终验收流程。
22. 文件采用单文件、多处引用：确认书文件实体归属项目确认书，同时通过关联关系出现在项目资料、合同归档和线索资料索引；合同详情只展示只读“关联确认书”，不复制进合同扫描件列表。

## 三、建议数据模型

```ts
type ProjectConfirmationCategory = 'stage' | 'general'
type ProjectConfirmationStatus =
  | 'draft' | 'company_sealed' | 'sent_to_customer'
  | 'customer_returned' | 'archived' | 'voided'

interface ProjectConfirmation {
  id: string
  projectId: string
  contractId: string
  category: ProjectConfirmationCategory
  typeId: string
  stageId?: string
  nodeId?: string
  reason?: string
  status: ProjectConfirmationStatus
  version: number
  supersedesId?: string
  currentVersionKey: string
  description: string
  companyFile: { docxFileId: string; pdfFileId: string; templateVersion: string; generatedAt: string; generatedBy: string; signingEntityId: string }
  sendRecord?: { recipient: string; channel: string; sender: string; sentAt: string; dueAt?: string; fileVersion: number }
  customerScan?: { packageId: string; primaryFileId: string; fileIds: string[]; uploadedBy: string; uploadedAt: string; version: number }
  archivedAt?: string
  archivedBy?: string
  createdAt: string
  updatedAt: string
}
```

`currentVersionKey` 由项目、合同、类型和阶段节点（通用确认书为空节点）组成；归档后新版本通过 `supersedesId` 连接旧版本，旧版本只读。

## 四、实现阶段

### 阶段 A：领域模型与纯函数

- 扩展 `ProjectConfirmation`，统一状态、版本、模板、发送和扫描件文件包字段。
- 提取类型配置、阶段/合同关联校验、版本递增、状态转移和归档前置条件纯函数。
- 增加逾期提醒投影规则：只生成待办，不改变确认书状态。
- 增加文件关联投影，确保项目资料、合同归档、线索索引只引用同一文件实体。

### 阶段 B：确认书页签与创建向导

- 在项目详情“确认书”页签增加“新建确认书”入口、类型筛选、状态筛选、当前版本/历史版本视图。
- 创建向导先选阶段/通用大类，再选管理员启用的类型；阶段类型必须选择交付节点，通用类型填写事由和日期。
- 自动带入项目、当前有效合同、客户、签约主体和负责人；需求变更类型展示补充报价关联位。
- 草稿只允许编辑说明文字，保存后形成版本化草稿。

### 阶段 C：模板生成与签章

- 接入确认书类型的 DOCX 模板版本；按字段映射填充模板，保留填充后的 DOCX 源文件。
- 导出不可编辑 PDF 并叠加合同签约主体的电子章，记录模板版本和生成元数据。
- 生成成功后正文锁定；失败或内容错误只能作废当前版本并新建版本。

### 阶段 D：发送、回签与归档

- 增加手动登记发送表单和回签截止日期；发送文件版本固定为当前盖章 PDF。
- 增加扫描件文件包上传，支持多文件和主文件选择；上传新版本不覆盖旧版本，状态保持“客户已回签”。
- 管理员提供“确认归档”动作，校验我方 PDF、客户扫描件包和合同关联均存在后归档。
- 归档后写入项目动态、交付节点确认书交付物和合同只读关联视图。

### 阶段 E：迁移、文档与回归

- 兼容现有 `ProjectConfirmation` 的 `已签署/待签署` mock 数据，迁移为新状态并保留历史附件。
- 对齐 PRD、项目详情 360 计划、功能看板和技术架构文档。
- 补齐纯函数、组件和 α 手走测试；确认书页签不影响现有验收流程与合同归档。

## 五、验收用例

1. 确认书页签可创建阶段/通用确认书；阶段类型缺节点或合同不可保存。
2. 管理员停用类型后，业务人员不能新建该类型，历史记录仍可查看。
3. 草稿只能编辑说明文字，不能改项目、合同、节点关联。
4. 生成后同时存在 DOCX 源文件和带章 PDF，PDF不可编辑且元数据完整。
5. 已发客户记录联系人、渠道、发送人、时间、文件版本和截止日期。
6. 超过截止日期只出现逾期提醒，主状态仍为已发客户。
7. 上传一个或多个 PDF/JPG/PNG 后进入客户已回签，并能指定主文件。
8. 扫描件不合格时操作人可直接上传新扫描件版本，不出现退回/作废按钮，旧文件保留。
9. 管理员仅在我方 PDF、客户扫描件包和合同关联齐全时可归档。
10. 同一项目/合同/类型/节点归档后新建 V2；V1 保留并显示已被替代，V2成为当前有效版本。
11. 阶段确认书归档只完成节点确认书交付物并写入项目动态；通用确认书不完成阶段。
12. 需求变更确认书与补充报价可任一先建，但生成补充合同前必须存在已归档确认书且完成互相关联。
13. 合同详情展示关联确认书只读视图，不复制文件；项目、合同、线索索引指向同一文件实体。

## 六、明确不做

- 不接入外部电子签署平台。
- 不设置确认书退回状态、退回按钮或强制退回原因。
- 不覆盖已归档版本或删除历史文件。
- 不把确认书并入最终验收单实体。
- 不复制文件到合同扫描件列表或维护第二套确认书台账。
