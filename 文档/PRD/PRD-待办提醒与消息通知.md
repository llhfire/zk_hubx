# HubX 待办提醒与消息通知 PRD

## 0. 文档说明

本文档用于指导 HubX 待办提醒与消息通知模块的产品评审、前端开发、PHP 后端开发、MySQL 数据库设计、企业微信接入、阿里云短信接入和测试验收。

1. `MUST` 表示必须实现，`SHOULD` 表示建议实现，`MAY` 表示可选实现。
2. 当前 HubX 为前端虚拟功能：待办、站内信和发送记录保存在浏览器本地；企业微信消息和阿里云短信仅模拟投递。
3. 正式版本必须由 PHP 服务端生成业务事件、待办和消息任务，并负责持久化、权限、幂等、重试、限流及审计。
4. 企业微信当前尚未创建自建应用，正式接入前必须由企业管理员完成应用创建、可见范围及消息发送权限配置。
5. 企业微信员工资料是员工主数据源，HubX 通过企业微信 UserId 与员工 ID 的绑定关系解析企业微信消息接收人。

## 1. 产品目标

本模块用于统一承接 HubX 中所有涉及员工的待处理事项和业务消息，解决以下问题：

- 员工无法集中查看分散在报价、合同、线索、项目、日报等模块中的待处理事项。
- 站内信、待办入口分散，图标重复，用户容易混淆。
- 同一业务事件在站内信、企业微信和短信之间缺少统一配置与追踪。
- 待办完成状态与实际业务状态不一致。
- 高优先级或超时事项缺少可配置的升级提醒。
- 管理员无法查询每条消息的接收人、通道和投递结果。

目标结果：

1. 登录用户名旁只保留一个“提醒中心”图标。
2. 提醒中心内统一展示待办与未读站内信。
3. 待办由业务事件自动生成，并由真实业务结果驱动完成或取消。
4. 消息通知按规则发送站内信、企业微信和阿里云短信。
5. 短信默认仅用于可配置的高优先级或超时升级场景。
6. 所有消息投递可查询、可追踪、可审计。

## 2. 需求范围

### 2.1 本期包含

- 统一提醒图标及提醒中心弹层。
- 待办中心。
- 业务待办自动生成、更新、完成和取消。
- 待办延后提醒。
- 企业微信行政审批待办的只读同步与外部处理入口。
- 站内信。
- 企业微信应用消息。
- 阿里云短信。
- 消息规则新增、编辑、启停和测试。
- 消息模板管理基础能力。
- 超时升级和短信限流。
- 消息发送记录查询、筛选、搜索、单条删除和批量删除。
- 消息发送失败记录与重试机制。

### 2.2 本期不包含

- 用户手工新建待办。
- 用户手工完成业务待办。
- 用户删除业务待办。
- 待办转派、共享、抄送或拆分。
- 独立的站内信图标。
- 独立的待办提醒图标。
- “全部站内信标为已读”按钮。
- 所有普通业务消息默认发送短信。
- 在 HubX 内处理请假、报销、出差、外出等企业微信行政审批。
- 邮件、微信公众号、钉钉、飞书等其他消息通道。
- 营销短信和群发短信。

## 3. 核心概念与边界

### 3.1 业务事件

业务模块状态发生变化后发布的标准事件，例如：

- 报价审批节点待处理。
- 合同审批通过。
- 技术评估指派。
- 线索跟进逾期。
- 项目任务转派。

业务事件是待办和消息的共同上游来源。

### 3.2 待办

待办代表“某位员工需要完成的业务动作”，必须具有明确负责人和处理入口。

待办不是普通通知，不能通过阅读消息完成，也不能由用户手工标记完成。

### 3.3 消息通知

消息用于告知员工业务变化。消息可通过站内信、企业微信或短信发送，不一定要求接收人执行操作。

### 3.4 提醒

提醒是待办或消息在特定时间再次触达用户的表现，包括：

- 待办角标。
- 延后到期后重新出现。
- 业务截止或超时提醒。
- 高优先级短信升级。

### 3.5 三者关系

一个业务事件可以：

- 只生成待办，例如周期性日报填写任务。
- 只发送消息，例如审批结果通知。
- 同时生成待办和消息，例如新的报价审批任务。

待办状态和消息已读状态相互独立：

- 阅读消息不会完成待办。
- 完成业务待办后，历史消息仍保留。
- 删除消息发送记录不会删除待办或改变业务状态。

## 4. 角色与权限

| 角色 | 权限 |
|---|---|
| 普通员工 | 查看本人待办和站内信；处理有权访问的业务；延后本人待办 |
| 业务负责人 | 查看本人及业务权限范围内的业务事项；接收相关通知 |
| 消息管理员 | 配置消息规则、模板和短信策略；查看发送记录 |
| 系统管理员 | 管理全部规则、通道配置和发送记录；处理异常 |

权限要求：

1. `MUST`：普通员工只能查询分配给自己的待办和发送给自己的站内信。
2. `MUST`：待办跳转后仍由业务模块再次校验操作权限。
3. `MUST`：消息管理员不得通过发送记录查看无权访问的完整敏感业务内容。
4. `MUST`：通道凭证、AccessKey、Secret 只允许授权管理员配置，前端不得回显完整值。
5. `MUST`：删除发送记录只删除日志展示，不影响真实业务、待办和第三方已发送消息。

## 5. 信息架构

### 5.1 顶部统一提醒入口

- 位置：登录用户名旁。
- 图标：只保留一个通知图标。
- 角标：展示“当前有效待办数 + 未读站内信数”的合计。
- 点击后打开提醒中心弹层。

### 5.2 提醒中心弹层

包含两个页签：

1. `待办 N`
2. `站内信 N`

页签数量分别表示：

- 待办：当前用户未完成且未取消的有效待办数量。
- 站内信：当前用户投递成功且未读的站内信数量。

底部入口：

- 查看全部待办。
- 查看全部站内信。

### 5.3 管理页面

- 待办中心：`/todos`
- 消息提醒设置：`/system/message-settings`
- 消息发送记录：`/system/message-center`
- 企业微信集成：`/system/wecom`

## 6. 待办中心

### 6.1 页面概览

顶部显示：

- 全部待处理。
- 高优先级。
- 今日截止。
- 已逾期。

统计数量必须基于当前用户有权查看的待办，并排除已完成、已取消及仍在延后时间内的待办。

### 6.2 列表视图

| 视图 | 说明 |
|---|---|
| 待处理 | 状态为待处理或处理中的有效待办 |
| 已完成 | 已由业务结果确认完成的待办 |
| 已取消 | 因业务撤销、流程作废或负责人变化而关闭的待办 |
| 全部 | 当前用户有权查看的全部待办 |

### 6.3 筛选与搜索

- 关键词：待办标题、内容、业务编号。
- 业务来源。
- 优先级。
- 支持分页。

默认排序：

1. 已逾期待办优先。
2. 优先级按高、中、低排序。
3. 同优先级按最早截止时间排序。
4. 无截止时间排在有截止时间之后。
5. 条件相同时按生成时间倒序。

### 6.4 列表字段

| 字段 | 说明 |
|---|---|
| 待办事项 | 标题、摘要；外部事项显示“企业微信”标识 |
| 业务来源 | 报价审批、合同审批、技术评估等 |
| 优先级 | 高、中、低 |
| 状态 | 待处理、处理中、已完成、已取消；可叠加“已逾期” |
| 生成时间 | 待办创建时间 |
| 截止时间 | 无截止时间时明确展示 |
| 操作 | 详情、去处理或去企业微信处理、延后 |

### 6.5 待办详情

至少展示：

- 待办标题和事项说明。
- 业务来源和业务编号。
- 负责人。
- 优先级和状态。
- 生成时间、截止时间。
- 是否逾期。
- 延后提醒时间，适用时展示。
- 业务处理入口。

页面提示：

> 业务待办不能手动完成或删除，请前往对应业务页面处理。

## 7. 待办生成与生命周期

### 7.1 待办来源

默认支持：

| 来源 | 典型事件 | 负责人 |
|---|---|---|
| 审批 | 报价或合同审批节点激活 | 当前审批人 |
| 技术评估 | 报价技术评估指派 | 被指派员工 |
| 线索跟进 | 新建跟进计划或跟进逾期 | 线索负责人 |
| 日报 | 到达日报填写时间 | 应提交日报的员工 |
| 项目任务 | 任务指派或转派 | 当前任务负责人 |
| 企业微信审批 | 企业微信待审批事项同步 | 企业微信审批人 |

系统必须支持后续业务模块通过统一接口动态接入，不限于以上固定来源。

### 7.2 唯一性

待办使用以下组合保证业务幂等：

`租户 ID + 待办来源 + 业务对象 ID + 任务类型 + 负责人 ID`

同一业务动作重复发送事件时，不得生成重复有效待办。

### 7.3 状态

| 状态 | 说明 |
|---|---|
| 待处理 | 已分配但用户尚未进入处理 |
| 处理中 | 用户已点击去处理，或业务模块已进入处理状态 |
| 已完成 | 真实业务动作已完成 |
| 已取消 | 业务已撤销、审批已作废、任务不再需要处理或已转派 |

点击“去处理”可以将待办标记为处理中，但不能标记为已完成。

### 7.4 完成规则

`MUST`：完成状态只能由对应业务模块的结果事件驱动。

示例：

- 审批任务在当前用户完成通过或驳回后完成。
- 或签任务由其中一人处理后，该人的任务完成，其他人的任务取消。
- 审批流程作废后，所有未完成任务取消。
- 技术评估提交并确认成功后完成。
- 日报成功提交后完成。
- 项目任务达到业务定义的完成状态后完成。

业务处理失败、仅打开页面或仅阅读通知均不能完成待办。

### 7.5 负责人变化

业务负责人发生转派时：

1. 原负责人的有效待办变为已取消。
2. 为新负责人生成新待办。
3. 保留原待办记录用于审计。
4. 分别按规则通知原负责人和新负责人。

### 7.6 外部企业微信待办

1. 请假、报销、出差、外出等审批仍在企业微信处理。
2. HubX 可只读展示同步到的企业微信待办。
3. 点击操作显示“去企业微信处理”，不得在 HubX 内提供通过或驳回。
4. 完成状态以企业微信回调或同步结果为准。
5. 企业微信数据无法同步时，不得由用户手工完成该待办。

## 8. 待办延后提醒

支持：

- 1 小时后提醒。
- 今天下班前提醒，默认 18:30。
- 明天上午提醒，默认 09:00。

规则：

1. 延后只影响提醒展示，不改变截止时间、业务状态和逾期计算。
2. 延后期间，待办中心仍可查询该待办，但顶部提醒弹层和角标可暂时隐藏。
3. 延后时间到达后，待办重新进入提醒列表。
4. 已完成或已取消待办的延后设置自动失效。
5. 已逾期的高优先级待办仍允许延后界面提醒，但不能阻止后台超时升级消息。
6. 延后不是免打扰，不影响管理员配置的企业微信或短信升级策略。

## 9. 优先级与逾期

### 9.1 优先级

| 优先级 | 适用场景 |
|---|---|
| 高 | 审批、技术评估、临近关键交付、已逾期事项 |
| 中 | 日常跟进、日报、项目任务 |
| 低 | 非紧急协作提醒和信息补充 |

优先级由业务事件或消息规则决定，普通员工不能自行修改。

### 9.2 逾期

当前时间晚于截止时间，且待办仍为待处理或处理中时，标记为已逾期。

逾期不是独立主状态，不改变待办原状态。

## 10. 消息通知规则

### 10.1 规则字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| 规则名称 | 是 | 便于管理员识别 |
| 业务模块 | 是 | 消息来源模块 |
| 触发事件 | 是 | 一个或一组明确事件 |
| 接收对象 | 是 | 支持多选 |
| 发送通道 | 是 | 站内信、企业微信、短信 |
| 优先级 | 是 | 高、中、低 |
| 超时升级时间 | 否 | 到期后升级提醒 |
| 启用状态 | 是 | 关闭后不产生新消息任务 |

### 10.2 默认业务规则

| 规则 | 事件 | 默认接收人 | 默认通道 | 优先级 |
|---|---|---|---|---|
| 线索分配提醒 | 分配、转移 | 业务负责人、被指派员工 | 站内信、企业微信 | 中 |
| 线索跟进逾期 | 跟进计划逾期 | 业务负责人、直属上级 | 站内信、企业微信；满足升级条件后短信 | 高 |
| 报价技术评估指派 | 技术评估人被指派 | 被指派员工 | 站内信、企业微信 | 高 |
| 报价审批及结果 | 提交、通过、驳回、作废 | 当前审批人、发起人 | 站内信、企业微信 | 高 |
| 合同审批及结果 | 提交、通过、驳回、作废 | 当前审批人、发起人、业务负责人 | 站内信、企业微信 | 高 |
| 项目任务 | 指派、转派、逾期 | 被指派员工、项目负责人 | 站内信、企业微信 | 中 |
| 财务事项 | 待处理、通过、驳回、逾期 | 当前处理人、发起人 | 站内信、企业微信 | 高 |
| 日报协作 | 评论、提及、退回 | 被提及员工、日报提交人 | 站内信、企业微信 | 低 |
| 员工组织变更 | 入职、转正、调岗、离职、同步异常 | 员工本人、部门负责人、管理员 | 站内信、企业微信 | 中 |

后续新增业务模块时，只要事件涉及员工，就必须评估是否生成待办或消息，并可新增对应规则。

### 10.3 接收对象

支持：

- 业务发起人。
- 业务负责人。
- 被指派员工。
- 当前审批人。
- 下一审批人。
- 抄送人。
- 部门负责人。
- 直属上级。
- 指定员工。
- 指定岗位。
- 指定部门。
- 系统管理员。
- 员工本人。
- 被提及员工。

服务端必须在事件发生时解析为稳定员工 ID，并去重。同一事件、同一接收人、同一通道只生成一条消息任务。

## 11. 消息通道

### 11.1 站内信

1. 站内信是 HubX 内的默认消息通道。
2. 投递成功后进入统一提醒入口的“站内信”页签。
3. 点击“查看详情”时标记该站内信已读，并跳转对应业务页面。
4. 站内信支持单条已读；不提供“一键全部已读”按钮。
5. 站内信删除只影响发送记录展示，不影响业务和待办。
6. 站内信内容可包含标题、摘要、业务模块、优先级、发送时间和跳转地址。

### 11.2 企业微信应用消息

正式发送前需要：

- 企业 ID `CorpID`。
- 自建应用 ID `AgentId`。
- 自建应用 Secret。
- 自建应用可见范围。
- 员工 HubX ID 与企业微信 UserId 的有效绑定。
- 企业微信应用消息发送权限。

通讯录 Secret 用于同步员工资料，不应与应用 Secret 混用。

规则：

1. 接收人无法解析企业微信 UserId 时，记录发送失败。
2. 已离职或停用员工不得继续发送。
3. 消息应包含简短摘要和 HubX 可访问链接。
4. 企业微信成功接收不等于用户已阅读；若无法取得已读回执，不展示虚假的已读状态。
5. 调用企业微信接口必须在服务端完成，Secret 不得发送到浏览器。

### 11.3 阿里云短信

短信采用可配置策略，默认不用于所有业务消息。

默认允许发送的情况：

- 规则优先级为高，且管理员明确启用短信通道。
- 待办超时达到配置的升级时长。
- 企业微信发送失败且规则允许短信降级。

短信配置：

- 启用状态。
- 短信签名。
- 模板 Code。
- 超时升级小时数。
- 系统每日发送上限。
- 单员工每日发送上限。
- 企业微信失败时短信降级。

发送前必须校验：

1. 员工存在有效手机号。
2. 手机号归属员工且允许用于业务通知。
3. 短信签名和模板已通过阿里云审核。
4. 未超过系统及员工限额。
5. 相同事件未在去重窗口内重复发送。

短信内容不得包含完整合同金额、客户隐私、审批意见等敏感内容，只提示业务类型、超时状态和登录系统处理。

## 12. 消息模板

### 12.1 模板类型

- 待办通知。
- 审批结果。
- 业务指派。
- 业务变更。
- 超时提醒。
- 短信升级。

### 12.2 模板变量

建议支持：

- `{{业务类型}}`
- `{{业务标题}}`
- `{{业务编号}}`
- `{{发起人}}`
- `{{负责人}}`
- `{{审批结果}}`
- `{{审批意见}}`
- `{{截止时间}}`
- `{{超时时长}}`
- `{{处理链接}}`

规则：

1. 模板保存时校验变量是否合法。
2. 发送前校验必需变量是否有值。
3. HTML 内容必须过滤危险标签和脚本。
4. 企业微信和短信模板允许按通道维护不同内容。
5. 短信模板必须匹配阿里云已审核的模板 Code。

## 13. 消息生成、投递与重试

### 13.1 消息生成

业务事件进入消息服务后：

1. 根据业务模块和事件匹配启用规则。
2. 解析接收人并去重。
3. 根据规则生成各通道消息任务。
4. 渲染对应消息模板。
5. 投递站内信，异步发送企业微信和短信。
6. 记录每个接收人、每个通道的独立发送结果。

### 13.2 幂等

建议使用：

`事件 ID + 规则 ID + 接收人 ID + 通道`

作为消息任务幂等键。重复消费同一事件不得重复发送。

### 13.3 投递状态

| 状态 | 说明 |
|---|---|
| 待发送 | 已生成任务，等待通道处理 |
| 发送中 | 正在调用第三方通道 |
| 成功 | 通道已接受或站内信已写入 |
| 失败 | 调用失败且仍可重试或已终止 |
| 未触发 | 不满足短信优先级、升级时长或其他策略 |

### 13.4 重试

1. 站内信写入失败：由事务回滚或消息队列重试。
2. 企业微信和短信临时失败：按退避策略自动重试。
3. 鉴权失败、模板无效、手机号为空等永久错误不自动无限重试。
4. 建议最多自动重试 3 次。
5. 每次尝试记录时间、响应码和脱敏后的失败原因。
6. 审批、合同等业务操作成功后，消息发送失败不得回滚业务结果。

## 14. 超时升级

1. 业务待办达到截止时间后标记逾期。
2. 规则配置超时升级时长后，从截止时间或首次待办时间开始计算。
3. 达到升级条件后，可增加直属上级、部门负责人或业务负责人为接收人。
4. 短信仅在规则启用短信且满足高优先级或超时升级条件时发送。
5. 同一待办同一升级层级只能触发一次。
6. 待办完成、取消或流程作废后，后续升级任务立即取消。
7. 用户延后界面提醒不影响后台超时升级。

## 15. 消息发送记录

### 15.1 页面定位

消息发送记录用于管理员查看站内信、企业微信和阿里云短信的投递情况，不作为业务处理入口。

### 15.2 筛选与搜索

- 关键词：消息标题、内容、事件编号。
- 业务模块。
- 接收人。
- 发送通道。
- 投递状态。
- 支持分页。

### 15.3 列表字段

- 消息标题与摘要。
- 业务模块。
- 接收人。
- 通道。
- 优先级。
- 投递状态。
- 失败、跳过或未触发原因。
- 发送时间。
- 操作：删除。

列表中不提供“去处理”、预览或下载等其他操作。

### 15.4 删除

1. 支持单条删除。
2. 支持勾选多条后批量删除。
3. 删除前二次确认。
4. 删除不撤回已发送的企业微信或短信。
5. 删除不改变站内信之外的业务状态和待办状态。
6. 正式系统建议采用逻辑删除，并保留管理员审计记录。
7. 安全审计需要保留的投递日志不得被普通消息管理员永久删除。

## 16. 统一提醒入口交互

### 16.1 待办页签

- 最多展示前 5 条有效待办。
- 优先展示已逾期和高优先级事项。
- 显示业务模块、标题、截止时间和优先级。
- 操作按钮为“去处理”或“前往企业微信”。
- 点击后进入业务页面；不能直接完成待办。

### 16.2 站内信页签

- 最多展示前 5 条未读站内信。
- 显示业务模块、标题和两行摘要。
- 点击“查看详情”后标记单条已读并跳转业务页面。
- 不显示“全部站内信标为已读”。

### 16.3 角标

1. 合计数量超过 99 时显示 `99+`。
2. 延后中的待办不计入角标，延后到期后重新计入。
3. 已读站内信不计入角标。
4. 待办完成或取消后实时扣减。
5. 多端登录时应通过轮询、WebSocket 或服务端推送保持数量同步。

## 19. 安全与合规

1. 企业微信 Secret、通讯录 Secret、阿里云 AccessKey 不得保存在前端或普通数据库明文字段。
2. 建议使用密钥管理服务或服务端加密存储。
3. 所有配置查看和修改必须记录管理员、时间及变更前后内容。
4. 手机号在页面和日志中默认脱敏。
5. 第三方接口响应不得记录 Token、Secret 或完整敏感消息正文。
6. 短信发送必须遵守阿里云模板、签名和频控要求。
7. 用户离职后立即停止生成新待办和消息，并关闭或转派其有效待办。
8. 消息跳转链接不得绕过 HubX 登录和业务权限校验。
9. 逻辑删除的发送记录按公司审计策略保留。

## 20. 监控指标

建议监控：

- 活跃待办数、已逾期待办数。
- 待办平均处理时长。
- 各业务模块待办完成率。
- 站内信未读率。
- 企业微信发送成功率。
- 短信发送成功率与每日用量。
- 失败重试次数。
- 接收人无法解析数量。
- 短信限流和未触发数量。
- 从消息点击到业务处理完成的转化率。

## 21. 验收标准

### 21.1 统一入口

- 登录用户名旁只显示一个提醒图标。
- 弹层内包含待办和站内信两个页签。
- 角标等于有效待办数与未读站内信数之和。
- 可以分别进入全部待办和全部站内信。
- 不存在第二个容易混淆的提醒图标。

### 21.2 待办

- 业务事件可以自动生成待办。
- 同一幂等事件不会生成重复待办。
- 待办不能手工新建、完成或删除。
- 点击去处理只进入业务页面，不直接完成待办。
- 业务完成后待办自动完成。
- 业务撤销、审批作废或负责人变化后待办自动取消。
- 支持 1 小时后、今天下班前、明天上午延后提醒。
- 延后不改变截止时间和逾期状态。
- 企业微信审批待办只能前往企业微信处理。
- 支持关键词、业务来源和优先级筛选。

### 21.3 站内信

- 投递成功的未读站内信进入统一提醒入口。
- 点击查看详情后仅将该条消息标记为已读。
- 不提供“全部站内信标为已读”按钮。
- 阅读消息不改变待办和业务状态。

### 21.4 企业微信

- 绑定有效企业微信 UserId 的员工可以收到应用消息。
- 未绑定、已离职或应用不可见的员工记录明确失败原因。
- 应用 Secret 只在服务端使用。
- 企业微信消息失败不回滚业务操作。

### 21.5 短信

- 普通低、中优先级消息默认不发送短信。
- 高优先级、超时升级或配置的企业微信失败降级可触发短信。
- 系统每日和单员工每日限额生效。
- 短信不包含敏感业务详情。
- 重复事件不会重复发送短信。

### 21.6 消息发送记录

- 支持按业务模块和接收人筛选。
- 支持按通道和投递状态筛选。
- 支持关键词搜索标题、内容或事件编号。
- 支持单条删除。
- 支持多选批量删除。
- 操作列只保留删除。
- 删除记录不影响待办、业务状态或已投递的第三方消息。

## 22. 待研发确认

以下事项不改变本 PRD 的产品边界，但正式接入前需要技术确认：

1. 业务事件采用数据库 Outbox、消息队列还是同步接口。
2. 顶部角标采用 WebSocket、SSE 还是短轮询。
3. 企业微信应用消息链接的域名、可信域名和移动端登录方式。
4. 阿里云短信签名、模板 Code 和 AccessKey 的正式配置。
5. 工作日历、下班时间和跨时区的截止时间计算。
6. 超时升级层级及每层接收人。
7. 消息发送记录和审计日志的保留期限。
8. 企业微信行政审批数据采用回调同步还是定时查询。
