# 01 · 范围与决策

## 一、用户下达的原话

> 「对前端进行最严格审查，原则上是每个页面都必须按定义的 UI 组件进行组织，如果确实 UI 组件则必须构建一个 UI 组件出来，放到组件库里面。组件库里的组件按类型分类，原则上一类组件只有一个版本，特殊情况允许有变体。先告诉我你怎么理解的。」

看完理解之后，用户批了 4 条决策：

| 决策 | 用户选择 | 含义 |
|---|---|---|
| 1 | **A** | Arco 算「已定义的 UI 组件」，页面可直接用；设计系统只收敛「组合用法 + 业务语义」，**不包 Arco 薄壳** |
| 2 | 可以 | 布局类 Tailwind / 内联样式允许；**视觉类（颜色 / 字号 / 圆角 / 阴影）禁止** |
| 3 | 新建设计系统 | 新建 `packages/ui/src/design-system/`，原 `packages/ui/src/app/components/ui/` **取消** |
| 4 | 全量迁移 | 全部页面都要迁，不做「先迁高危」 |

执行方式（贯穿全程）：改代码用 codex cli，复核用 grok cli，我做终检。
用户后来说「全部改造，一直做完」，因此本次做到门禁全 0 才算收口。

## 二、为什么「不包薄壳」

判断标准来自 `docs/design-system/设计系统规范.md` §二：

> **如果一个组件只是把 Arco 的 props 原样转发，它不该存在。**

反例 `HxButton` / `HxSelect`：只做 `<Button {...props} />`，等于多一层要维护的映射，
出问题时还得翻两个文件才知道 prop 去哪了。而 Arco 本身已经是完整的组件库。

设计系统只承担两类职责：

| 职责 | 例子 | 为什么必须由设计系统做 |
|---|---|---|
| **组合用法固化** | `DataTable` = Table + 工具栏 + 空态 + 加载 + 分页 | 这套组合每个页面都写一遍，必然漂移（某页忘了空态、某页工具栏放右边） |
| **业务语义封装** | `StatusTag` = 状态 → 文案 + 色彩 | 「已驳回」到底红还是橙，不该由 20 个页面各自决定 |

界线：**同一语义 + 同一 props 契约 = 变体；语义不同 = 新组件。**
`ContractStatusTag` 与 `QuoteStatusTag` 若都是「状态 → 色彩 + 文案」，就是一个 `StatusTag` + 两张映射表。

## 三、为什么全量迁移而不是只改高危

全量迁移的代价是 257 个文件、+14147 / −12672 行。收益是四类问题一次性消灭：

1. **同一语义多实现**：合同状态色在 7 个文件各写一份，同一个「已驳回」有 3 种红。
2. **静默失效**：Arco 对未知 prop **丢弃不报错**，`<Card bodyStyle>` 之类写错了看不出来。
   换成设计系统组件后，prop 是显式声明的，写错 tsc 直接报。
3. **规则靠人记**：M-001~M-049 是行为规则文档，没人会每次翻。固化进组件后，
   规则变成默认行为（例如 `AlertBanner` 的关闭 ≠ 已处理，注释就写在 props 上）。
4. **新人没有参照物**：`/ui-library` 之前只有 8 个组件有样子，等于没有样板。

只改高危的话，剩下的会继续把下一批同类缺陷藏在「看起来对」的代码里。

## 四、刻意划出的边界（这些没做）

| 没做 | 原因 |
|---|---|
| 不封装 Arco 薄壳 | 用户决策 1.A，见上 |
| 不改业务逻辑、不动数据形状 | 本次是 UI 组织层改造，业务行为必须逐字不变 |
| 不删页面的 `useState` / mockData | 那是 α 版数据策略，与组件化无关 |
| 不给 `RichTextEditor` 加设计系统样式 | 它依赖 Quill 自带 toolbar CSS，强行接管会和 Quill 主题打架 |
| 不把文档复刻组件（报价单 A4 缩略图）拉进字号阶梯 | 它是 1:1 复刻纸张排版，5.5~13px 是缩印尺寸，登记为 `facsimile` 例外 |
| 不合并「回款计划表」等 3 个 ⏳ 组件 | 4 处列结构不同（计划 vs 开票 vs 预测），需先定「列模式」，见 [09](09-下次待办.md) |
