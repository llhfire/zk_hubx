# 新增日报与日报配置 PRD（工程开发指导版）

## 0. 给开发者和 AI 的执行说明

本文档用于指导真实工程中的前端、后端和测试开发。实现时遵守以下原则：

1. `MUST` 表示必须实现，`SHOULD` 表示建议实现，`MAY` 表示可选实现。
2. 先复用现有项目中的用户、组织、岗位、项目、线索、权限和日报模型，不重复建立同义模型。
3. 固定枚举与可配置数据必须分开：工作归属是固定枚举，工作性质和日报项目是可配置数据。
4. 生产环境必须通过服务端持久化配置和日报数据，不得将 `localStorage` 作为最终数据源。
5. 历史日报必须保存关联对象名称快照。配置停用、改名或删除后，不得改变历史日报展示。
6. 提交日报必须具备防重复提交能力；日报主记录与工作项明细应在同一事务中保存。
7. 字段名可以根据现有代码规范调整，但业务语义、校验和数据来源必须保持一致。
8. 本期不设计项目阶段。成本分析通过工作归属、关联对象、工作性质和工时完成。

## 1. 需求范围

### 1.1 本期包含

- 新增日报统一弹窗。
- 顶部日历入口和日报列表入口。
- 员工、部门、岗位自动带出。
- 一份日报包含多条工作项。
- 工作性质按岗位读取。
- 工作归属与关联对象联动。
- 日报提交校验及任务明细生成。
- 日报配置中的岗位工作性质维护。
- 日报配置中的日报项目维护。

### 1.2 本期不包含

- 日报草稿和自动保存。
- 日报审批、撤回和提交后编辑。
- 日报附件上传。
- 第三方系统自动同步工作内容。
- 配置批量导入、导出。
- 项目阶段维护。
- 成本报表页面；本期只保证数据可用于后续成本归集。

## 2. 领域定义

### 2.1 固定工作归属

工作归属的展示顺序和业务编码必须固定。

| 顺序 | 编码 | 展示名称 | 关联对象类型 |
|---|---|---|---|
| 1 | `development` | 开发 | 外部开发项目 |
| 2 | `operations` | 运营 | 日报项目 |
| 3 | `software_presales` | 软件售前 | 软件售前线索 |
| 4 | `immigration_presales` | 移民售前 | 日报项目 |
| 5 | `promotion` | 推广 | 日报项目 |
| 6 | `ecommerce` | 电商 | 日报项目 |

说明：编码可适配现有工程命名，但前后端必须使用同一套稳定值，不得使用中文名称作为数据库主键。

### 2.2 关键术语

| 术语 | 定义 |
|---|---|
| 工作性质 | 员工具体做了什么，例如需求分析、功能开发、线索跟进；按岗位配置 |
| 工作归属 | 工作成本归属于哪类业务，固定为六类 |
| 关联对象 | 工作归属下的具体项目、线索或日报项目 |
| 日报项目 | 运营、移民售前、推广、电商下可配置的二级归集对象 |
| 工作项 | 日报中的一条任务明细，独立记录性质、归属、内容和工时 |
| 名称快照 | 工作项提交时保存的关联对象名称，用于保证历史数据不随配置变化 |

## 3. 模块一：新增日报

### 3.1 功能入口

- `MUST`：点击顶部日历图标打开“填写日报”弹窗。
- `MUST`：点击“日报列表 > 新增日报”打开同一个弹窗。
- `MUST`：两个入口复用同一组件、初始化逻辑、校验规则和提交接口。
- `MUST`：每次重新打开弹窗时创建新的填写会话，不残留上一次未提交数据。

### 3.2 初始化数据

打开弹窗时至少需要以下上下文：

| 数据 | 数据来源 | 规则 |
|---|---|---|
| 日报日期 | 服务端业务日期或客户端当前日期 | 默认当天，页面只读 |
| 撰写人 | 当前登录账号关联的员工档案 | 页面只读 |
| 部门 | 员工当前所属组织 | 页面只读 |
| 岗位 | 员工当前岗位 | 页面只读 |
| 日报模板 | 现有岗位或角色模板规则 | 决定可展示的补充字段 |
| 工作性质选项 | 日报配置中的当前岗位配置 | 按配置顺序展示 |

`MUST`：日期计算统一使用业务时区，当前项目默认 `Asia/Shanghai`。

`MUST`：服务端提交时重新校验当前用户身份、部门和岗位，不信任客户端传入的员工身份信息。

### 3.3 页面字段

| 字段 | 必填 | 可编辑 | 数据来源或规则 |
|---|---|---|---|
| 日期 | 是 | 否 | 默认当天日期 |
| 撰写人 | 是 | 否 | 当前登录员工 |
| 部门 | 是 | 否 | 当前员工所属组织 |
| 岗位 | 是 | 否 | 当前员工岗位 |
| 工作性质 | 是 | 是 | 按当前岗位读取配置项 |
| 工作归属 | 是 | 是 | 固定六类 |
| 关联对象 | 是 | 是 | 根据工作归属联动加载 |
| 工作内容 | 是 | 是 | 员工填写 |
| 工时 | 是 | 是 | 数值且大于 0 |
| 明日工作计划 | 是 | 是 | 日报级字段 |
| 其他模板字段 | 按模板 | 是 | 沿用现有销售、开发、投放或通用模板规则 |

### 3.4 关联对象数据来源

| 工作归属 | 数据来源 | 查询条件 | 默认选择 |
|---|---|---|---|
| 开发 | 项目管理 | 外包业务线且状态不是已完成 | 不默认，员工选择 |
| 运营 | 日报配置 > 日报项目配置 > 运营 | 只读取启用项 | 默认排序第一项 |
| 软件售前 | 线索管理 | 当前用户有权访问的可用软件售前线索 | 不默认，员工选择 |
| 移民售前 | 日报配置 > 日报项目配置 > 移民售前 | 只读取启用项 | 默认排序第一项 |
| 推广 | 日报配置 > 日报项目配置 > 推广 | 只读取启用项 | 默认排序第一项 |
| 电商 | 日报配置 > 日报项目配置 > 电商 | 只读取启用项 | 默认排序第一项 |

### 3.5 字段联动规则

1. `MUST`：切换工作归属时清空原关联对象的 ID、名称和类型。
2. `MUST`：清空后加载新工作归属对应的关联对象选项。
3. `MUST`：运营、移民售前、推广、电商只展示启用的日报项目。
4. `MUST`：日报项目按 `sortOrder` 升序展示；排序相同时按项目名称排序。
5. `MUST`：当配置类工作归属存在可选项时，默认选择排序第一项。
6. `MUST`：开发项目和软件售前线索由员工手动选择，不自动选中。
7. `MUST`：对应工作归属没有可用关联对象时展示空状态，并禁止提交该工作项。
8. `SHOULD`：关联对象数量较多时支持关键字搜索。

### 3.6 工作项规则

- `MUST`：一份日报可以新增多条工作项。
- `MUST`：每条工作项独立保存工作性质、工作归属、关联对象、工作内容和工时。
- `MUST`：未提交的工作项可以删除。
- `MUST`：至少存在一条有效工作项才能提交。
- `MUST`：工作项提交时保存关联对象 ID、类型和名称快照。
- `SHOULD`：每条工作项使用稳定的临时 ID，避免前端增删造成列表状态错乱。

### 3.7 提交校验

校验顺序建议从页面级到工作项级执行：

1. `MUST`：明日工作计划不能为空。
2. `MUST`：至少有一条有效工作项。
3. `MUST`：每条有效工作项必须选择工作性质。
4. `MUST`：每条有效工作项必须选择工作归属及关联对象。
5. `MUST`：每条有效工作项必须填写工作内容。
6. `MUST`：每条有效工作项工时必须大于 0。
7. `MUST`：所有工作项总工时不得超过 24 小时。
8. `MUST`：总工时超过 12 小时时进行二次确认。
9. `MUST`：提交失败时保留当前填写内容，不关闭弹窗。
10. `MUST`：提交进行中禁用重复提交。

以下规则尚未在产品需求中确定，开发前不得自行假设：

- `DECISION_NEEDED`：工时允许的最小单位和小数精度。
- `DECISION_NEEDED`：同一员工同一天是否只允许一份日报。
- `DECISION_NEEDED`：是否允许补填历史日期的日报。

### 3.8 提交结果

提交成功后生成：

1. 一条日报主记录。
2. 与有效工作项数量一致的日报工作项明细。

建议的数据结构如下，字段名可按现有工程规范调整：

```ts
type WorkAttributionCategory =

interface DailyReport {
```

### 3.9 成本归集预留

日报工作项必须保留后续成本计算所需的最小数据：

- 员工 ID。
- 部门 ID。
- 岗位 ID。
- 日报日期。
- 工作性质。
- 工作归属。
- 关联对象 ID 和类型。
- 工作时长。

后续可使用“员工标准时薪 × 工作项工时”计算人工成本，并按关联对象汇总。

## 4. 模块二：日报配置

日报配置包含“岗位工作性质”和“日报项目配置”两个子模块。配置权限只授予日报管理员或具备对应权限的角色。

### 4.1 岗位工作性质

#### 4.1.1 数据来源

- 部门与岗位树：读取公司组织架构及岗位数据。
- 工作性质列表：读取选中岗位的工作性质配置。
- 初始配置：使用系统预设数据初始化，之后由管理员维护。

#### 4.1.2 页面规则

1. `MUST`：左侧使用部门和岗位组成的树形结构。
2. `MUST`：选择岗位后，右侧显示该岗位的工作性质列表。
3. `MUST`：工作性质按列表顺序展示，并在新增日报中使用相同顺序。
4. `MUST`：支持新增、编辑、删除、上移、下移和恢复默认。
5. `MUST`：名称去除首尾空格后不能为空。
6. `MUST`：同一岗位内工作性质名称不可重复。
7. `MUST`：工作性质最多 20 个字符。
8. `MUST`：不同岗位的配置互相独立。

#### 4.1.3 建议数据结构

```ts
interface PositionWorkNatureConfig {
  id: string;
  positionId: string;
  name: string;
  sortOrder: number;
  isSystemDefault: boolean;
  createdAt: string;
  updatedAt: string;
}
```

建议数据库约束：

- 同一 `positionId` 下，标准化后的 `name` 唯一。
- `sortOrder` 为正整数。
- 删除配置前不修改历史日报；历史日报依赖名称快照。

### 4.2 日报项目配置

#### 4.2.1 固定业务类型

日报项目只维护以下四类：

| 编码 | 名称 |
|---|---|
| `operations` | 运营 |
| `immigration_presales` | 移民售前 |
| `promotion` | 推广 |
| `ecommerce` | 电商 |

#### 4.2.2 列表与表单字段

| 字段 | 必填 | 规则 |
|---|---|---|
| 业务类型 | 是 | 使用左侧当前类型，新增或编辑时不可跨类型修改 |
| 项目名称 | 是 | 最多 30 个字符，同一业务类型内不可重名 |
| 启用状态 | 是 | 默认启用 |
| 排序 | 是 | 大于等于 1 的整数，数字越小越靠前 |
| 备注 | 否 | 最多 100 个字符 |

#### 4.2.3 维护规则

1. `MUST`：左侧展示四个固定业务类型，默认选中运营。
2. `MUST`：右侧列表展示项目名称、状态、排序和操作。
3. `MUST`：支持新增和编辑日报项目。
4. `MUST`：支持直接启用或停用项目。
5. `MUST`：系统默认项目不能删除，只能停用。
6. `MUST`：管理员新增的项目可以删除；生产工程建议使用软删除。
7. `MUST`：同一业务类型内项目名称不可重复。
8. `MUST`：配置变更后，新打开的日报读取最新配置。
9. `MUST`：已经打开的日报在提交时，服务端重新校验关联项目是否仍可用。
10. `MUST`：停用或删除配置不影响历史日报展示。

#### 4.2.4 默认项目

| 业务类型 | 默认项目 |
|---|---|
| 运营 | 人员招聘、工资核算、行政管理、报销审批、财务管理、运营推广、企业活动、培训、内部会议、其他 |
| 移民售前 | 俄罗斯移民、新加坡移民 |
| 推广 | IP打造、代运营、其他 |
| 电商 | 微商城、助农电商 |

默认项目应通过初始化脚本或种子数据写入，不要在多个前端组件中重复硬编码。

#### 4.2.5 建议数据结构

```ts
interface DailyProjectConfig {
  id: string;
  category: 'operations' | 'immigration_presales' | 'promotion' | 'ecommerce';
  name: string;
  enabled: boolean;
  sortOrder: number;
  remark?: string;
  isSystemDefault: boolean;
  deletedAt?: string | null;
  createdAt: string;
  updatedAt: string;
}
```

建议数据库约束：

- 同一 `category` 下，未删除记录的标准化名称唯一。
- `sortOrder >= 1`。
- 系统默认记录禁止物理删除。

## 5. 服务端能力要求

不强制接口路径，但服务端必须提供以下能力：

| 能力 | 输入 | 输出 |
|---|---|---|
| 获取日报初始化上下文 | 当前登录用户 | 日期、员工、部门、岗位、模板、岗位工作性质 |
| 获取关联对象选项 | 工作归属、关键字、分页参数 | 当前用户有权限访问的项目、线索或日报项目 |
| 提交日报 | 日期、明日计划、工作项列表、幂等键 | 日报 ID、总工时、提交状态 |
| 获取组织岗位树 | 无或组织范围 | 部门和岗位树 |
| 维护岗位工作性质 | 岗位及配置内容 | 最新配置 |
| 查询日报项目配置 | 业务类型 | 配置列表 |
| 新增或编辑日报项目 | 配置字段 | 最新配置记录 |
| 启停或删除日报项目 | 配置 ID | 操作结果 |

## 6. 权限与数据安全

- `MUST`：普通员工只能以当前登录身份提交本人日报。
- `MUST`：关联项目和线索必须经过服务端数据权限过滤。
- `MUST`：日报配置接口必须校验管理员权限。
- `MUST`：客户端传入的部门、岗位、关联对象名称不能作为可信数据。
- `MUST`：提交日志应记录提交人、提交时间和请求标识，便于定位重复提交。
- `SHOULD`：配置编辑使用版本号或更新时间进行并发控制，避免覆盖他人修改。

## 7. 异常处理

| 场景 | 预期行为 |
|---|---|
| 当前员工无部门或岗位 | 显示明确错误并禁止提交，提示联系管理员完善员工档案 |
| 当前岗位无工作性质 | 工作性质显示空状态并禁止提交，提示管理员配置 |
| 当前工作归属无关联对象 | 关联对象显示空状态并禁止提交 |
| 关联对象在填写期间被停用 | 服务端拒绝该工作项，前端保留内容并提示重新选择 |
| 网络或服务端失败 | 不关闭弹窗，不清空已填写内容 |
| 重复点击提交 | 前端禁用按钮；服务端通过幂等键返回同一结果 |
| 配置名称修改 | 新日报读取新名称，历史日报继续显示提交时快照 |
| 配置被删除 | 新日报不再展示，历史日报不受影响 |

## 8. 验收标准

### 8.1 新增日报

- `AC-DR-001`：两个入口打开同一个填写日报弹窗。
- `AC-DR-002`：日期、撰写人、部门、岗位自动带出且不可修改。
- `AC-DR-003`：工作性质根据当前员工岗位读取配置。
- `AC-DR-004`：工作归属按固定六类及固定顺序展示。
- `AC-DR-005`：切换工作归属后清空原关联对象并加载新数据。
- `AC-DR-006`：运营、移民售前、推广、电商默认选中排序第一的启用项目。
- `AC-DR-007`：开发项目和软件售前线索不自动选择。
- `AC-DR-008`：一份日报可以新增和删除多条工作项。
- `AC-DR-009`：缺少明日计划、工作性质、关联对象、工作内容或有效工时时不能提交。
- `AC-DR-010`：总工时超过 24 小时时不能提交。
- `AC-DR-011`：总工时超过 12 小时时出现二次确认。
- `AC-DR-012`：提交成功后生成一条日报主记录和对应数量的工作项明细。
- `AC-DR-013`：提交失败后弹窗和已填写数据保持不变。
- `AC-DR-014`：重复提交不会生成重复日报或重复工作项。

### 8.2 岗位工作性质

- `AC-CFG-001`：组织树按部门和岗位展示。
- `AC-CFG-002`：选择岗位后展示该岗位独立的工作性质配置。
- `AC-CFG-003`：支持新增、编辑、删除、排序和恢复默认。
- `AC-CFG-004`：同一岗位内不允许空名称或重复名称。
- `AC-CFG-005`：修改后，新打开的日报按最新顺序显示工作性质。

### 8.3 日报项目配置

- `AC-CFG-006`：固定展示运营、移民售前、推广、电商四类。
- `AC-CFG-007`：支持新增、编辑、启停和排序。
- `AC-CFG-008`：同一业务类型内不允许空名称或重复名称。
- `AC-CFG-009`：系统默认项目不能删除，自定义项目可以删除。
- `AC-CFG-010`：停用项目不出现在新日报中。
- `AC-CFG-011`：项目按排序值升序展示，排序相同时按名称排序。
- `AC-CFG-012`：配置停用、改名或删除后，历史日报仍显示原名称。

## 9. 测试建议

至少覆盖以下测试层级：

1. 单元测试：工作归属映射、排序、默认选中、总工时计算和字段校验。
2. 组件测试：入口打开弹窗、工作归属联动、多工作项增删、提交失败保留数据。
3. 接口测试：权限过滤、唯一约束、启停状态、幂等提交和事务回滚。
4. 集成测试：岗位配置变更后新增日报读取最新数据。
5. 回归测试：配置停用、改名或删除后历史日报显示不变。

## 10. 推荐开发顺序

1. 统一领域枚举和数据模型。
2. 完成岗位工作性质和日报项目的服务端持久化。
3. 完成日报初始化上下文和关联对象查询能力。
4. 完成新增日报弹窗及两个入口复用。
5. 完成工作归属联动、多工作项和提交校验。
6. 完成事务提交、名称快照和幂等处理。
7. 补齐权限、异常处理及自动化测试。
