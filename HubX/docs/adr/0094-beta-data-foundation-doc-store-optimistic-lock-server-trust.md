# β 数据底座：D1 文档式存储维持，乐观锁 + actor/时钟服务端可信

β 期继续用 D1 的 `data` 列存整条领域对象 JSON（文档式），不做关系建模。代价是不能按状态/客户高效查询、无引用完整性，换取每个域一张表、读写路径与前端 Service 接口一一对应。这是有意识的阶段性决策，β 稳定后若出现「按列表查询慢/要跨域报表」再拆列，不提前。

但三个可信度问题必须在 β 修掉，否则审批与审计链路无意义：

1. **乐观锁**：PUT 请求体必须带 `version`，与服务端当前值不匹配返回 409。现状是「GET-改-PUT 整对象」，多用户并发互相静默覆盖。
2. **actor 服务端化**：会签人/盖章人/操作人不再信任前端传入的字符串。登录认证（「基础工具」planned）落地前，过渡方案是请求头 `X-Actor` 由网关注入/前端统一携带，服务端记录；认证落地后换成会话身份。
3. **服务端时钟**：`updatedAt` / 事件时间 / 盖章时间由 Workers 生成，客户端 `now()` 只作展示参考。

曾考虑直接上关系建模 + 行级权限（β 只有 2 个域上线，迁移成本远大于收益）和 JWT 登录一步到位（阻塞主线，登录认证按看板节奏另做）。
