## 坑 1：批量正则改 TSX，会把原问题换成更难查的问题

**现象**：用 Python 批量把 `<Card>` → `<SectionCard>`，产生了四类垃圾：

- 脚本用 `s.find('export ')` 切文件，只匹配 `<Card ` 和 `<Card>` 两种字面量，
  **多行 `<Card\n` 全部漏掉** —— 改了一半，看起来「已经迁完」；
- 闭标签 `</Card>` 残留 → 一堆 `TS17002`；
- 生成 `bordered=None`（Python `None` 直接进源码）→ 语法错；
- 反斜杠被写进源文件（22 个语法错误）。

**为什么**：多行 JSX 属性不存在「安全的正则」。标签可能跨行、可能嵌套、
可能出现在字符串里。

**决策**：

```python
# ✅ 只用于单行、结构确定的替换
s = re.sub(r'<Card(?![A-Za-z])', '<SectionCard', s)   # 覆盖多行开标签
s = re.sub(r'</Card>', '</SectionCard>', s)
```

超过一个标签层级、或涉及三目/嵌套，就**逐文件 Edit**，不要批量。
每跑一次批量替换，**立刻跑一遍 tsc** 再继续。
（本次 tsc 报语法错时会**跳过语义检查**，所以「输出为空」必须配合「确认真的遍历完」一起看，见坑 4。）

## 坑 2：迁移脚本写「跳过逻辑」会死循环

**现象**：Tag 迁移脚本加了「已经是 StatusTag 就跳过」的判断，第二次运行直接挂死。
`kill` 掉后重写为：单次扫描 + `edits` 数组倒序应用 + `open_end` / `match_close`
（支持嵌套闭合）。

**决策**：批量脚本**幂等性靠「单次扫描 + 一次性应用」实现，不靠「跳过」**。
要重跑就先 `git diff` 确认上次改了什么。

## 坑 3：`Type 'string' is not assignable to type 'StatusTone'` 批量爆发

**现象**：`*_LABELS[x].color` 全部报 TS2322，几十条。

**为什么**：映射表的定义是 `{ label: string; color: string }`，
`color` 是自由字符串，页面把它传给 `StatusTag` 的 `tone` 自然不匹配。

**错误的修法**：在调用处 `as StatusTone` 强转 —— 那等于把类型检查关掉。

**正确的修法**：**改定义本身**

```diff
- const SLA_LABELS: Record<string, { label: string; color: string }> = { … };
+ const SLA_LABELS: Record<string, { label: string; tone: StatusTone }> = { … };
```

改完后，**当初写错的色值（比如把「已驳回」写成 `'orange'`）会在定义处直接报错**。
这就是类型检查的价值所在。

## 坑 4：tsc 有语法错时会跳过语义检查

**现象**：批量替换后跑 `tsc`，只报了 2 条 TS2322，以为快好了；
实际是语法错误让编译器提前中止，剩下的 300 条根本没检查。

**判别**：

- 正常的 0 错误：**完全没有任何输出**。
- 语法错误：会先报 `TS1005`（`'}' expected`）、`TS1382`（unexpected token）、
  `TS17002`（expected corresponding JSX closing tag）—— **这些必须先全部修完**，再看语义报错。

**决策**：验证链里 tsc 跑完要**看错误码类型**，不看数量。语法错优先。

## 坑 5：JSX 里注释的位置有两种写法是语法错误

- **开标签内部不能写 `//`**：`<Pie /* 这里 */ …>` 或 `<Table\n// 注释\n data=…>`
  都报 `TS1005/TS1382`。
- **`{cond && (` 或 `{cond ? (` 之后不能紧跟 `{/* */}`**：会变成两个并列表达式，报 `TS17002`。

正确位置：注释放在整个元素之前（JSX children 位置，`{/* */}` 形式），或删掉。

## 坑 6：两处误改的 `</StatusTag>` 与误用的 `tabIndex`

**现象**：

- `LeadDetail360` 的 `checkable` Tag、`Stage3WebAutomation` 的 `closable` Tag
  闭标签被批量改成了 `</StatusTag>`，与开标签 `<Tag` 不配对；
- `SalesDailyTemplate` 给 `StatusTag` 传了 `tabIndex` / `role` / `onKeyDown`，
  而 `StatusTag` 已经内建这些（当 `onClick` 存在时）。

**为什么**：批量替换只看开标签，闭标签按同名逻辑替换，但有的 `<Tag>` 是**故意保留**的。

**决策**：迁移后用 `grep -c '<Tag[^A-Za-z]'` 和 `grep -c '</StatusTag>'`
做**配对核验**；组件已经内建的 a11y 属性不要重复传，否则 `StatusTagProps` 里没有它会报错
（这也是好事——说明类型真的在拦）。

## 坑 7：新测试文件里不能写 `const { X, type Y } = await import('..')`

**现象**：esbuild 报 `Expected "}" but found "StatusMap"`。

**为什么**：`type` 修饰符只在 TS 的 import/export 语法里合法，
解构赋值里写 `type Y` 是非法语法。

**修法**：顶层 `import { StatusTag, resolveStatus } from '..'`
+ `import type { StatusMap } from '..'`，删掉动态 import。

## 坑 8：`onOk: () => Message.success(...)` 类型不匹配

**现象**：`Type '() => MessageType' is not assignable to type '() => void | Promise<void>'`。

**为什么**：`Message.success()` 返回 `MessageType`（可 `then` 的句柄），不是 `void`。
箭头函数隐式返回它。

**修法**：加花括号让它不返回值 —— `onOk: () => { Message.success('已提交'); }`。

**同类**：任何 `onXxx?: () => void` 的回调，里面调 `Message` / `Notification` /
`Modal.confirm` 都要注意返回值。

## 坑 9：Arco 的 `Select.renderTag` 与 `StatusTag` 签名不兼容

**现象**：`MetaPanel` 的下拉多选已选项，`onClose` 传进来的是 `(event)`，
而 `StatusTag` 的 `onClose` 是 `() => void`。

**决策**：**这一处保留 Arco `Tag`，并写注释说明它是输入控件不是状态标签**。
同时门禁的 `rawTagColor` 把 `closable` / `checkable` / `onClose` / `onCheck`
列为豁免关键词。

理由：设计系统的目标是「同一语义只有一个实现」，而「下拉选项的已选值」
和「业务状态」是**两个语义**，不该强行合并。

## 坑 10：测试超时不是并发问题，是「整页渲染 + 4 个 Provider」

**现象**：`ContractDetail.test.tsx` 在全量并发跑时超 5000ms，单独跑通过。

**为什么**：该用例渲染整个 `ContractDetail` 页面，包含 4 个 Context Provider，
一次完整渲染接近 5s；并发时 CPU 抢占让它跨过默认超时。

**决策**：该用例超时放到 `20_000` 并加注释说明原因，**不降低断言强度**。
（避免的做法：把测试改成浅渲染 —— 那会失去整页回归的价值。）

## 坑 11：浏览器滚动容器不是 `window`

**现象**：`window.scrollTo(0, y)` 后截图，页面纹丝不动。

**为什么**：这个应用的外壳是 Arco Layout，滚动发生在 `main.arco-layout-content` 上
（`overflow-y: auto`），`document.body` 高度只有一屏。

**修法**：

```js
document.querySelector('main.arco-layout-content').scrollTop = y;
```

**通用做法**：截图长页面前先找出真正的滚动容器 ——
`[...document.querySelectorAll('*')].filter(e => e.scrollHeight > e.clientHeight + 100 && ['auto','scroll'].includes(getComputedStyle(e).overflowY))`。

## 坑 12：ego-browser 的 `taskSpace` / `page` 参数是名称不是自造标签

**现象**：

- `taskSpace()` 无参 → `taskSpace expects a task-space name (non-empty string) or numeric id`；
- `t.page("ui1")` → `page label not found: ui1. Managed Pages in task space 21: p1`。

**修法**：`await taskSpace("smoke")`（名称任意），页面用**已存在的标签** `p1`，
或 `await task.newPage()` 新建。

## 坑 13：门禁自己会漏检 —— `borderBottom` 这类分写属性

**现象**：全天都在说「hardcodedColor = 0」，收尾时发现
`borderBottom: '1px solid #f2f3f5'` 从没被扫到。

**为什么**：门禁的键名正则是 `color|backgroundColor|background|fontSize|…|border`，
**`borderTop` / `borderRight` / `borderBottom` / `borderLeft` / `borderColor` / `outline` /
`fill` / `stroke` 一个都不在**。

**修法**：键名扩到 17 个，并验证过能抓：

```
borderTop: '1px dashed #e5e6eb'  →  hardcodedColor: 1 > 预算 0  ✗
```

**教训**：**门禁说 0，只代表「门禁定义的口径下是 0」。**
收口时要用另一种口径独立复核一遍（本次用同规则的变体脚本全量重扫，
`facsimile` 文件也扫，结果 0 处），而不是只看那行「通过」。

## 坑 14：`libraryMissingDemo` 不能只做全文匹配

**现象**：第一版检查用 `libraryText.includes(name)`，全过。
但目录表里明明写着 `component: 'MoneyText'` —— **组件没渲染，检查照样通过**。

**修法**：去掉 import 段 + 把所有字符串字面量替换成 `''`，再匹配。
自测（故意加假导出）能报错，才算真能拦。

**教训**：写门禁要**自测它能拦住违规**，否则可能只是个安慰剂。

## 决策：为什么用 CSS 变量注入色板，而不是内联 style

`/ui-library` 要展示 9 个 tone 的真实颜色。写法有两种：

```tsx
// A：内联 style
<span style={{ background: STATUS_TONE_VARS[t].bg, color: STATUS_TONE_VARS[t].fg }} />

// B：CSS 变量注入（本次采用）
<span style={{ '--ui-swatch-bg': STATUS_TONE_VARS[t].bg } as CSSProperties} />
/* CSS */ .ui-library-tone-swatch { background: var(--ui-swatch-bg); }
```

A 能通过门禁（门禁只扫字符串字面量里的色值，`STATUS_TONE_VARS[t].bg` 是表达式），
但**B 更好**：视觉样式留在 CSS，页面只负责「把哪个 tone 传进去」，
与其他组件的分工一致。

## 决策：怀疑内容丢失时的核查方法

迁移中出现 5 处「文案好像没了」。核查步骤（每次都一样）：

1. `git diff` 找到删除的那一行，确认删的具体是什么；
2. `grep` 这个文案在所有 `types.ts` / `utils.ts` 里的新位置；
3. 确认是「合并进共享映射表」还是「改由组件内部渲染」；
4. 在交接文档里逐条登记去处。

**5 处全部确认是合并/内部渲染，无内容丢失。**
登记本身比结论重要 —— 下次迁移时能对照着查。
