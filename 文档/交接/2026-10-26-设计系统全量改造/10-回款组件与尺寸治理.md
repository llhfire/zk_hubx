## 2. 用户规则与不可回退约束

### 2.1 页面组件铁律

页面构建或修改时，必须从 `@/design-system` 取组件。现有组件不恰当时，先构建受限变体或新组件，再完成：

- 设计系统出口导出；
- TypeScript 接口；
- 组件测试；
- `/ui-library` 实样；
- 设计系统门禁；
- 至少一个真实业务页面接入。

禁止在业务页面直接从 Arco 取 `Card`、`Table`、`Tag`、`Progress`、`Alert` 等组件，也禁止用局部 JSX/CSS 绕过组件库。

### 2.2 尺寸治理原则

组件存在不等于组件已经合格。尺寸需要同时看：

- 组件自身的默认尺寸与受限变体；
- 组件所在的业务容器宽度；
- 内容密度与文字层级；
- 桌面宽屏、1440px 和窄屏的响应式行为；
- 组件库实样是否还原真实使用场景。

不能用“全部 `width: 100%`”解决尺寸问题，也不能用统一缩放掩盖组件比例不合理。表格、归档面板等确实需要占满容器的组件可以保持宽幅；金额摘要、选择器、期次横线等组件必须在实样页提供真实业务宽度基准。

## 3. 回款组件现状

### 3.1 `PaymentAmountSummary`

文件：

`HubX/packages/ui/src/design-system/business/PaymentAmountSummary.tsx`

职责：合同金额列的紧凑摘要，只表达“合同额”和“待收”，并可选渲染回款期次横线。

接口：

```ts
interface PaymentAmountSummaryProps {
  total: number;
  receivable: number;
  scheduleItems?: PaymentScheduleItem[];
  size?: 'small' | 'default';
  className?: string;
}
```

当前约束：

- `small` 形态用于合同列表金额列；
- 金额统一消费 `MoneyText variant="compact"`；
- 不再显示“已收”长文案，避免合同列表列过度拥挤；
- `width: 100%` 是让它填充父级业务列，不代表它应当在所有演示场景中占满整行。

### 3.2 `PaymentScheduleRail`

文件：

`HubX/packages/ui/src/design-system/business/PaymentScheduleRail.tsx`

职责：每条细横线代表一期回款计划，线段长度代表比例，颜色表达回款状态。

接口：

```ts
interface PaymentScheduleItem {
  id?: string | number;
  label: string;
  percentage: number;
  amount: number;
  allocated: number;
  status: 'paid' | 'partial' | 'overdue' | 'upcoming' | 'pending';
  expectedDate?: string;
}
```

当前视觉契约：

| 状态 | 表达 | 实现 |
|---|---|---|
| `paid` | 已收足 | 蓝色纯色线段 |
| `partial` | 部分已收 | 一条连续 SVG 渐变线：蓝色向浅灰平滑过渡 |
| `overdue` | 已逾期 | 红色纯色线段 |
| `pending` | 待收 | 浅灰纯色线段 |
| `upcoming` | 即将到期 | 浅灰纯色线段 |

当前尺寸契约：

- SVG viewBox：`0 0 100 14`；
- CSS 交互区域高度：`14px`；
- 线段本体高度：`3px`；
- 线段实际位置：`y=5.5`；
- 线段之间使用比例相关间隔；
- 小尺寸 rail 最小宽度约 `92px`，实际宽度由业务父容器决定；
- 合同列表当前业务列约 `250px`，浏览器实测 rail 约 `230px`。

### 3.3 部分回款渐变实现

部分回款在 `PaymentScheduleRail` 中通过每个 partial 期次的独立 `linearGradient` 实现：

- 已收侧使用 `var(--ds-tone-info-fg)`；
- 未收侧使用 `var(--ds-tone-neutral-border)`；
- 渐变中点按 `allocated / amount` 计算；
- 在中点前后各留出过渡区，避免出现硬切割；
- partial 只渲染一条完整 rect，不再同时渲染 paid rect 与 unpaid rect；
- 渐变 ID 使用 React `useId()` 派生，避免多个 rail 实例 ID 冲突。

不要把 partial 渐变改成硬编码 RGB，也不要把所有状态都改成渐变。渐变只服务于“部分已收”的比例语义。

### 3.4 悬停与可访问性

当前 rail 的交互：

- 鼠标移动按 SVG 横向比例命中具体期次；
- 只显示当前悬停期次的 tooltip；
- tooltip 展示期次、比例、应收金额、已收金额、状态和预计日期；
- 当前期次 `<g>` 使用 `transform="translate(0, -1)"` 上移 1px；
- 当前期次同步使用设计系统阴影 token；
- SVG 有 `role="img"` 和总期次数 `aria-label`；
- SVG 可获得焦点，键盘聚焦默认展示第 1 期信息。

## 4. `/contracts` 接入现状

文件：

`HubX/packages/ui/src/app/pages/sales/contracts/Contracts.tsx`

当前接入：

- `合同 / 回款金额` 列宽已从约 `190px` 调整到 `250px`；
- 已移除外层导致 shrink-to-content 的 Arco `Space` 包裹；
- `PaymentAmountSummary` 直接填充该表格单元格；

## 5. 组件库实样尺寸治理

文件：

- `HubX/packages/ui/src/app/pages/ui-library/UiComponentLibraryPage.tsx`
- `HubX/packages/ui/src/app/pages/ui-library/UiComponentLibraryPage.css`

### 5.1 已完成的尺寸展示基准

新增实样容器类：

| 类名 | 最大宽度 | 适用组件 |
|---|---:|---|
| `.ui-library-size-stage--control` | `320px` | `UserPicker` 等单控件 |
| `.ui-library-size-stage--amount` | `260px` | `PaymentAmountSummary` |
| `.ui-library-size-stage--rail` | `360px` | `PaymentScheduleRail` |

这些宽度是组件库实样的展示基准，不是组件的全局固定宽度。业务页面仍通过父容器决定实际可用宽度。

### 5.2 保持宽幅的组件

以下组件的宽幅是语义要求，不要为了尺寸审美强行缩窄：

- `DataTable`；
- `PaymentPlanTable`；
- `FileArchivePanel`；
- `RichTextEditor`；
- `DocumentActionRow` 在列表行场景；
- `FormGrid` 的字段网格；
- `ProcessOverview` 和长流程详情工作区。

它们的审计重点是列比例、内容密度、断点行为和最小可读宽度，而不是简单设置 `max-width`。

### 5.3 下一批尺寸审计顺序

按风险和复用范围排序：

3. 表单组件：`FilterBar`、`FormSection`、`FormGrid`、`UploadPanel`、`RichTextEditor`、`UserPicker`。
4. 业务组件：`PaymentProgress`、`PaymentPlanTable`、`ProcessRecordCard`、`ProcessPanelSection`、`ApprovalFlow`、`DocumentActionRow`。
5. 宽屏/窄屏专项：`SplitLayout`、`FeatureWorkloadMatrix`、`EvaluationWorkloadTable`、`DormitoryRoomBoard`。

进度：标签与 `MetricCard` 见切片 11，展示组件见切片 12，表单组件见切片 13，业务组件见切片 14，宽窄屏见切片 15。五组到此结束。第 1 组里的 `Button`、`Input`、`Select`、`DatePicker`、`OrderedStatePicker` 没有单独开组。尺寸收口后的背景层次见切片 16，不要再把演示区改成深灰。

每个组件必须记录：默认尺寸、small/large 变体、最小宽度、推荐业务容器、窄屏行为、空值/长文本行为。没有明确尺寸契约的组件不能继续被新页面直接复用。

## 9. 已知问题与判断边界

- 本次只完成了组件库尺寸治理的第一批，不能宣称所有组件尺寸已经完成校准。
- 组件库实样目前仍有部分旧的通用布局，需要按第 5.3 节继续审计。
- `visualInlineStyle=2039` 是棘轮指标，当前门禁要求不增长；不要为了视觉尺寸审计把视觉样式重新写回页面内联 style。
- `facsimile` 目录是报价单/A4 纸张复刻例外，不得把其极小字号、固定比例和纸张尺寸规则泛化到普通业务组件。
- `PaymentScheduleRail` 的渐变只表达 partial；如果后续需要“逾期部分渐变”或“多次回款分段”，先新增明确业务状态契约，不要复用 partial 语义。
- 遇到“组件不好看”不能直接在业务页面加私有 CSS；必须回到组件、变体、token 或实样容器层解决。
