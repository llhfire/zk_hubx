## 一、线索基础状态

### 1. 线索类型 `clue_type`

|值|含义|
|---|---|
|1|公海线索|
|2|已领取/已分配线索|
|3|垃圾线索|
|4|高科技线索，控制器中单独使用|

线索状态 `cust_status` 中，代码明确使用了：

- `1`：分配/公海初始状态
- `3`：垃圾线索
- `11`：成交/已成交
- `15`：领取或分配后的状态

## 二、线索添加规则

### 1. 前端必填项

新增表单要求：

- 线索名称：必填，最长 30 个字符
- 来源：必填
- 所属公司：必填
- 初始信息：必填，前端限制最长 500 个字符

其他常见字段：

- 联系人
- 电话
- 微信
- 客户预算
- 优化师
- 负责人
- 协助人
- 备注
- 关键词
- 威客 ID
- 任务编号
- 标签
- 附件

表单规则见：[CluesFormModal.vue](/Users/mac/code/zkcrm/zkcrm_local/web/src/views/clues/components/CluesFormModal.vue)。

### 2. 后端必填项

后端验证器实际启用的规则只有：

- `name`：必填，最长 30
- `source`：必填
- `company_id`：必填且必须为数字

`init_info`、电话、微信、备注等字段的后端验证目前没有启用，部分规则处于注释状态。

见：[CluesValidate.php](/Users/mac/code/zkcrm/zkcrm_local/app/adminapi/validate/clues/CluesValidate.php)。

### 3. 联系方式规则

新增时，控制器中“电话和微信至少填写一个”的校验已被注释，因此当前代码允许：

- 电话为空
- 微信为空
- 电话和微信同时为空

但是修改时会强制要求：

> 电话或微信至少填写一个，不能同时为空。

这造成了“新增允许空联系方式，修改不允许”的前后端不一致。

### 4. 重复线索规则

新增时会检查以下任一字段是否重复：

- 电话
- 微信
- 威客 ID
- 任务编号

只要任意一个字段与已有线索相同，就拒绝新增。

错误提示为：

> 联系电话,微信,威客ID,任务编号 有重复记录，录入失败

注意：该重复检查主要在 `save()` 新增逻辑中，修改逻辑没有执行同样的重复检查，因此修改后可能产生重复联系方式或威客信息。

### 5. 部门与来源限制

销售部门 ID 为：

```
28、31、32
```

这些部门只能录入来源 ID：

```
8、自拓
1、威客
```

其他部门不受该限制。

### 6. 默认归属规则

新增时：

- 创建人自动取当前登录用户
- 优化师、负责人、协助人默认值为 `0`
- 如果指定负责人，则：
    - `clue_type = 2`
    - 记录 `owner_time`
- 如果没有负责人，服务层不会显式设置 `clue_type`，实际类型依赖数据库默认值

### 7. 标签和附件

- 标签以数组形式提交，后端以分号字符串保存
- 附件通过 `file_ids` 关联
- 新增、修改都支持多附件
- 后端会记录新增操作日志

## 三、线索列表规则

### 1. 主要列表接口

|页面|接口|默认条件|
|---|---|---|
|公海线索|`/clues`|`clue_type = 1`|
|我的线索|`/clues/myclues`|`owner_user_id = 当前用户`|
|全部线索|`/clues/allclues`|默认排除高科技线索|
|已分配线索|`/clues/allocated_clues`|`clue_type = 2`|
|垃圾线索|`/clues/trashclues`|`clue_type = 3`|
|我录入的|`/clues/cluesByoptimizer`|`optimizer_user_id = 当前用户`|
|我协助的|`/clues/cluesByassistant`|`assistant_user_id = 当前用户`|
|高科技线索|`/clues/hightech_clues`|`clue_type = 4`|
|跟进列表|`/clues/all_record` 等|按跟进记录筛选|

### 2. 默认排序

- 普通线索列表：创建时间倒序
- 已分配线索：`last_time` 升序，优先显示长时间未跟进的线索
- 跟进记录：创建时间或记录 ID 倒序

### 3. 支持的搜索字段

主要包括：

- 线索名称
- 线索 ID
- 电话
- 微信
- 威客 ID
- 任务编号
- 联系人
- 来源
- 所属公司
- 客户等级
- 客户状态
- 线索级别
- 优化师
- 负责人
- 协助人
- 客户 ID
- 创建时间
- 下次跟进时间
- 最近跟进内容
- 垃圾原因

其中：

- `key` 模糊搜索：名称、电话、微信、威客 ID、任务编号
- 电话搜索实际同时匹配电话和微信
- 多选条件通常使用 `whereIn`
- 创建时间、下次跟进时间支持时间区间

### 4. 快捷筛选

代码中有以下快捷条件：

|快捷条件|实际代码逻辑|
|---|---|
|今日未跟进|`next_time < 今天开始时间`|
|S 类客户|`customer_level = 4`|
|AB 类客户|`customer_level in [1,2]`|
|今日已跟进|`next_time > 今天开始时间`|

“今日已跟进”的实现并没有限制到今天结束时间，因此实际可能包含未来安排的跟进时间。

### 5. 已分配列表特殊规则

已分配列表额外限制：

- 必须是 `clue_type = 2`
- 排除负责人 ID 为 `37` 的数据
- 排除客户状态 `cust_status = 11` 的成交线索
- 按最近跟进时间升序

### 6. 列表展示的计算字段

服务层会额外计算：

- 跟进次数
- 最近跟进时间
- 最近跟进内容
- 下次跟进时间
- 负责人持续天数
- 历史负责人
- 威客链接
- 是否需要标红

标红规则：

- 已领取
- 未成交
- 下次跟进时间已过期，或最近一次跟进早于今天

### 7. 数据权限现状

当前代码存在权限范围风险：

- `getAllList()` 明确注释为“不验证数据范围”
- 线索详情 `read()` 的数据权限校验被注释
- 前端可以访问全部线索接口时，后端没有统一执行数据范围限制
- “我的线索”主要通过 `owner_user_id = 当前用户` 过滤
- 跟进汇总列表则按跟进记录创建人执行数据范围过滤

## 五、线索跟进规则

### 1. 跟进新增字段

跟进记录包括：

- 跟进方式：必填
- 客户状态：必填
- 客户级别：可选
- 跟进内容：必填
- 下次跟进时间：可选
- 成本小时
- 成本分钟
- 附件

后端规则：

- `record_type` 必须是合法类型
- `data_id` 必填
- `content` 必填，最长 1000 字符

前端内容框限制为 2000 字符，因此前端允许提交的长度超过后端限制，超过 1000 字符会被后端拒绝。

见：

- [RecordValidate.php](/Users/mac/code/zkcrm/zkcrm_local/app/adminapi/validate/record/RecordValidate.php)
- [CreateRecordModal.vue](/Users/mac/code/zkcrm/zkcrm_local/web/src/views/components/CreateRecordModal.vue)

### 2. 默认下次跟进时间

新建跟进时，前端默认：

> 次日 10:00:00

### 3. 新增跟进后的数据变化

新增跟进会：

- 将同一线索之前的待跟进记录标记为已处理
- 更新线索最近跟进时间
- 更新最近跟进内容
- 更新最近跟进人
- 有下次跟进时间时更新线索 `next_time`
- 同步客户状态和客户级别
- 保存跟进附件
- 记录跟进行为日志

### 4. 跟进列表分类

跟进页面包含：

- 全部跟进
- 今日待跟进
- 今日已跟进
- 超期未跟进

具体逻辑：

- 今日待跟进：下次跟进时间在今天，并且状态为待跟进
- 今日已跟进：创建时间在今天
- 超期未跟进：下次跟进时间早于当前时间，并且状态为待跟进
- 超期查询代码实际限制为最近 3 天，注释写的是“3 个月”，代码和注释不一致

### 5. 跟进修改和删除时间限制

后端规则：

- 跟进创建超过 24 小时后，不能修改
- 跟进创建超过 24 小时后，不能删除

前端按钮显示还额外要求：

- 当前时间已经到达下次跟进时间
- 且记录创建时间在 24 小时以内

因此前端比后端限制更严格。

### 6. 跟进权限现状

跟进修改、删除接口中未发现明确的：

- 创建人校验
- 线索负责人校验
- 线索数据权限校验

跟进汇总列表有数据范围过滤，但单条跟进的修改和删除权限相对宽松。

另外，编辑跟进时如果把下次跟进时间清空，服务层没有明确清除线索原有 `next_time`，可能造成线索仍显示旧的下次跟进时间。

## 六、线索修改规则

### 1. 修改表单字段

编辑时可以修改：

- 名称
- 来源
- 所属公司
- 联系人
- 电话
- 微信
- 客户预算
- 负责人
- 优化师
- 协助人
- 客户等级
- 客户状态
- 线索级别
- 客户
- 销售组信息
- 原型链接
- 威客 ID
- 任务编号
- 关键词
- 初始信息
- 备注
- 标签
- 创建时间
- 附件

`create_time` 在编辑表单中可以被修改，实际相当于允许修改线索录入时间。

### 2. 优化师修改限制

编辑已有线索时：

- 如果当前用户 `is_edit_optimizer != 1`
- 优化师字段会被前端禁用

但这只是前端限制，后端权限逻辑主要判断负责人和优化师的数据范围，并没有完全按照前端禁用逻辑执行。

### 3. 修改必填规则

后端修改时强制：

- 电话和微信至少一个不为空

前端还会对以下字段做限制：

- 名称最长 30
- 初始信息最长 500
- 备注最长 500
- 销售组启用时，销售组信息必填
- 客户预算不能小于 0
- 成本、金额类字段使用数字格式

其中销售组信息、初始信息、备注等规则主要是前端限制，后端验证器并未全部启用。

### 4. 修改权限

后端权限大致分为：

- 超级管理员：允许修改
- 普通管理员：允许修改
- 其他用户：
    - 负责人或优化师必须在自己的数据权限范围内
    - 或当前用户属于允许的数据范围
    - 主要围绕 `owner_user_id` 和 `optimizer_user_id` 判断

数据范围包括：

- 全部数据
- 自定义部门
- 个人数据
- 本部门及下级部门
- 本部门数据

需要注意：

- 协助人不是主要权限判断字段
- 创建人不是主要权限判断字段
- `update()` 使用提交过来的数据做权限判断，而不是完全使用数据库原始数据，存在权限判断被提交参数影响的风险

### 5. 领取、分配、退回、标记垃圾

这些也属于线索修改行为：

#### 领取

- 只能领取非 `clue_type = 2` 的线索
- 设置当前用户为负责人
- 设置 `clue_type = 2`
- 记录领取时间
- 客户状态设置为 `15`

#### 分配

必须提交：

- 线索 ID 数组
- 负责人 ID
- 分配原因

分配后：

- 设置 `clue_type = 2`
- 设置负责人和负责人时间
- 保存分配原因
- 如果原状态是垃圾状态 `3`，会调整为 `15`

#### 退回公海

必须提交：

- 线索 ID
- 退回原因

处理后：

- `clue_type = 1`
- `cust_status = 1`
- 保存退回原因

同一线索第三次退回公海时，会自动标记为垃圾线索。

#### 标记垃圾

- 手工标记要求普通管理员权限
- 自动标记使用固定原因时允许系统执行
- 设置：
    - `clue_type = 3`
    - `cust_status = 3`
    - 垃圾原因
    - 垃圾操作人
    - 垃圾时间

#### 删除

删除不是进入垃圾箱，而是物理删除：

- 删除线索
- 删除相关跟进记录
- 删除操作日志
- 删除关联数据

删除前仍需通过线索权限校验。

#### 转客户

转客户时：

- 需要通过数据权限校验
- 需要通过客户信息验证
- 创建客户数据
- 回写线索 `customer_id`
- 设置 `is_transform = 1`
- 同步线索历史跟进记录到客户

## 七、当前最重要的代码问题

1. 新增允许电话、微信都为空，但修改不允许。
2. 新增有重复检查，修改没有完整重复检查。
3. 前端跟进内容允许 2000 字，后端只允许 1000 字。
4. `getAllList()` 不执行统一数据范围限制。
5. 线索详情 `read()` 的权限校验被注释。
6. 跟进修改、删除缺少明确的创建人或负责人校验。
7. “今日已跟进”条件实际上包含未来的下次跟进时间。
8. 超期跟进代码限制为 3 天，但注释写的是 3 个月。
9. 编辑跟进清空下次跟进时间时，线索旧的 `next_time` 可能不会被清除。
10. 新版详情页没有完整展示转客户、删除等已有后端能力。
11. 线索修改权限主要判断负责人和优化师，协助人、创建人不在主要权限判断范围内。
12. 新增未指定负责人时，`clue_type` 依赖数据库默认值，不在服务层明确设置。
