# HubX 审批流程管理 PRD

## 0. 文档说明

本文档用于指导 HubX 审批流程管理的产品评审、前端开发、PHP 后端开发、MySQL 数据库设计和测试验收。

1. `MUST` 表示必须实现，`SHOULD` 表示建议实现，`MAY` 表示可选实现。
2. 当前 HubX 页面为 React 前端虚拟功能，数据主要保存在浏览器本地，不代表已具备真实审批、持久化或消息投递能力。
3. 正式版本必须由 PHP 服务端完成流程实例生成、审批权限校验、并发控制、状态流转、审计记录和消息事件发布。
4. 审批人、发起人、业务归属和操作权限不得信任前端传值，服务端必须根据登录态与配置重新计算。
5. 本 PRD 不采用审批流程版本化。模板或业务审批配置发生实质调整时，使用旧配置且仍在进行中的流程必须作废。

## 1. 产品背景与目标

HubX 负责合同、报价等偏业务性质的审批；请假、报销、出差、外出等行政审批继续在企业微信中处理。

本模块目标：

- 为 HubX 业务提供统一、可动态扩展的审批能力。
- 将流程结构与具体业务审批人配置分离，减少重复配置。
- 支持报价审批、合同审批，并允许后续新增其他业务审批。
- 为审批待办、站内信、企业微信消息及短信升级提供统一事件来源。
- 保留完整审批过程，保证审批结果可追溯。

## 2. 需求范围

### 2.1 本期包含

- 审批模板管理。
- 业务审批配置。
- 新增其他类型的 HubX 业务审批。
- 报价审批。
- 合同审批；合同新建、合同变更、合同作废统一归入合同审批，不拆分流程类型。
- 单人审批、或签、会签三种节点策略。
- 具体人员、上一节点负责人两种审批人来源。
- 通过、驳回两种审批操作。
- 驳回后返回发起人，由发起人重新发起。
- 模板或业务配置调整后，作废受影响的进行中审批。
- 待我审批、我发起的、我已处理、全部审批等查询。
- 审批详情、节点记录及业务页面跳转。
- 审批事件与消息提醒模块联动。

### 2.2 本期不包含

- 独立的“审批类型管理”或“类型注册”页面。
- HubX 内处理请假、报销、出差、外出等企业微信行政审批。
- 审批流程版本管理及旧版本继续运行。
- 自由退回到任意历史节点。
- 转交、加签、减签、委托、撤回、催办、抄送操作。
- 条件分支、并行分支、子流程。
- 审批人按角色、部门负责人、岗位或表达式动态计算。
- 除通过、驳回以外的审批动作。
- 发起人直接修改被驳回的原流程后继续审批。

## 3. 核心概念

| 概念 | 定义 |
|---|---|
| 审批模板 | 只定义节点名称、顺序和节点审批策略，不配置具体审批人 |
| 业务审批配置 | 定义业务名称、业务编码、绑定模板及各节点审批人 |
| 审批实例 | 某次业务提交后，根据当时有效配置生成的实际审批流程 |
| 审批节点实例 | 审批实例中的单个执行节点，保存实际审批人和处理结果 |
| 业务对象 | 发起审批的报价、合同或后续接入的其他 HubX 业务记录 |
| 上一节点负责人 | 上一节点最终使该节点完成并流转的审批人 |

## 4. 角色与权限

| 角色 | 主要权限 |
|---|---|
| 普通员工 | 发起有权操作的业务审批；查看本人发起、本人处理或本人有业务权限的审批 |
| 审批人 | 查看分配给本人的待审批事项；执行通过或驳回 |
| 业务管理员 | 新增和维护业务审批配置；查看配置预览 |
| 系统管理员 | 管理审批模板和业务审批配置；查看全部审批及作废记录 |

权限要求：

1. `MUST`：只有当前待处理节点的有效审批人可以操作审批。
2. `MUST`：服务端在提交审批决定时重新校验审批实例、节点状态和当前用户身份。
3. `MUST`：审批历史一旦生成不得被普通用户编辑或删除。
4. `MUST`：配置权限与审批操作权限分离。
5. `MUST`：查看审批详情和关联业务页面时，同时校验审批数据权限与业务数据权限。

## 5. 信息架构

### 5.1 审批中心

- 待我审批
- 我发起的
- 我已处理
- 企业微信审批
- 全部审批

企业微信审批仅作为只读记录查看入口；实际处理仍跳转或引导至企业微信，不在 HubX 内执行审批。

### 5.2 审批管理

- 审批模板
- 业务审批配置

不提供“审批类型管理”菜单。业务审批类型由“新增业务审批”直接创建和配置。

## 6. 审批模板

### 6.1 模板列表

列表字段：

| 字段 | 说明 |
|---|---|
| 模板名称 | 模板名称及模板编号 |
| 适用说明 | 模板适用的业务场景 |
| 审批流程 | 按顺序显示发起、审批节点、结束 |
| 业务使用 | 当前绑定该模板的业务审批数量 |
| 状态 | 启用或停用 |
| 最后更新 | 最近一次保存时间 |
| 操作 | 编辑、复制、删除 |

### 6.2 新建与编辑模板

基础字段：

| 字段 | 必填 | 规则 |
|---|---:|---|
| 模板名称 | 是 | 1～50 字，同一租户内不可重复 |
| 适用说明 | 否 | 最多 200 字 |
| 审批节点 | 是 | 至少 1 个，按页面顺序执行 |

节点字段：

| 字段 | 必填 | 规则 |
|---|---:|---|
| 节点名称 | 是 | 1～30 字 |
| 审批策略 | 是 | 单人审批、或签、会签 |
| 驳回规则 | 固定 | 驳回至发起人 |

节点支持新增、删除和调整顺序；至少保留一个审批节点。

### 6.3 节点策略

| 策略 | 审批人数 | 通过条件 | 驳回条件 |
|---|---:|---|---|
| 单人审批 | 1 人 | 该审批人通过 | 该审批人驳回 |
| 或签 | 2 人及以上 | 任意一人通过 | 任意一人驳回 |
| 会签 | 2 人及以上 | 所有人通过 | 任意一人驳回 |

`MUST`：或签节点完成后，其他尚未处理的人员任务自动关闭，不再允许操作。

`MUST`：会签过程中任意一人驳回后，节点立即结束，其他尚未处理任务自动关闭。

### 6.4 模板状态与操作限制

1. 已绑定业务审批的模板不得删除。
2. 已绑定启用中业务审批的模板不得停用。
3. 复制模板时生成新的模板编号，节点结构复制，但不复制业务绑定关系。
4. 编辑模板节点名称、数量、顺序或策略属于实质调整。
5. 实质调整保存前必须二次确认，并明确提示将作废受影响的进行中审批。
6. 仅修改模板说明不作废进行中审批。

## 7. 业务审批配置

### 7.1 业务审批列表

列表字段：

| 字段 | 说明 |
|---|---|
| 业务审批 | 业务名称、业务编码、说明 |
| 审批模板 | 当前绑定模板 |
| 审批流程 | 节点数量 |
| 状态 | 启用或停用 |
| 最近更新 | 最近保存时间 |
| 操作 | 配置、预览 |

系统默认提供：

1. 报价审批，业务编码建议为 `QUOTATION`。
2. 合同审批，业务编码建议为 `CONTRACT`。

允许管理员通过“新增业务审批”增加其他 HubX 业务审批。

### 7.2 业务信息

| 字段 | 必填 | 规则 |
|---|---:|---|
| 业务审批名称 | 是 | 1～50 字 |
| 业务编码 | 是 | 字母开头，仅允许大写字母、数字和下划线；创建后不可修改 |
| 业务说明 | 否 | 最多 200 字 |
| 审批模板 | 是 | 只能选择已启用模板 |
| 启用状态 | 是 | 默认启用 |

业务编码必须在同一租户内唯一，并由业务模块在发起审批时使用。

### 7.3 节点审批人配置

审批人来源只提供：

1. 具体人员。
2. 上一节点负责人。

选择规则：

| 节点策略 | 具体人员 | 上一节点负责人 |
|---|---|---|
| 单人审批 | 只能单选 1 人 | 运行时解析为 1 人 |
| 或签 | 必须多选，至少 2 人 | 不允许配置 |
| 会签 | 必须多选，至少 2 人 | 不允许配置 |

`MUST`：第一个审批节点不能选择“上一节点负责人”，因为不存在可解析的上一审批节点。

`MUST`：单人审批选择具体人员时只能单选；或签、会签选择具体人员时使用多选。

`MUST`：人员选择范围仅包含在职且具备 HubX 账号的员工。

### 7.4 上一节点负责人解析

“上一节点负责人”统一解析为上一节点最终完成审批的人：

| 上一节点策略 | 当前单人节点取得的审批人 |
|---|---|
| 单人审批 | 上一节点实际审批人 |
| 或签 | 实际点击通过并使节点完成的人 |
| 会签 | 最后一位点击通过并使节点完成的人 |

补充规则：

1. 上一节点被驳回时流程已结束，不生成当前节点任务。
2. 上一节点人员配置多人但节点尚未完成时，不提前创建当前节点任务。
3. 当前节点生成时，必须将解析后的员工 ID 固化到节点实例中，后续人员资料变化不影响已生成任务。
4. 配置页提示文案：`上一节点为多人审批时，将由该节点最终完成审批的人处理当前节点。`

### 7.5 审批人为空

本期不支持“审批人为空时跳过”。

当具体审批人离职、停用、无 HubX 账号或无法解析上一节点负责人时：

1. 不得自动跳过该节点。
2. 不得静默指派给其他人员。
3. 业务提交前可发现时，阻止发起并提示管理员检查审批配置。
4. 运行中才发现时，将实例标记为“审批异常”，通知系统管理员处理。

### 7.6 配置预览

预览必须按执行顺序展示：

`发起人提交 → 节点 1 → 节点 2 → … → 审批结束`

每个节点显示节点名称、审批策略、审批人来源和已配置人员。

## 8. 业务接入规则

### 8.1 报价审批

1. 报价业务提交审批时，使用启用中的 `QUOTATION` 配置。
2. 审批实例必须关联线索 ID、报价记录 ID、报价名称或摘要、报价金额和发起人。
3. 审批通过后，报价进入业务定义的“已通过”状态。
4. 审批驳回后，报价回到可修改状态，由发起人调整后重新发起。
5. 再次发起必须生成新的审批实例，不复用被驳回实例。

### 8.2 合同审批

1. 合同新建、合同变更和合同作废统一使用 `CONTRACT` 配置。
2. 不为合同变更、合同作废创建独立审批类型或独立流程配置。
3. 审批实例中应保存业务动作标识，例如新建、变更、作废，用于标题和详情展示，但不影响流程选择。
4. 审批通过后，由合同模块根据业务动作执行对应状态变更。
5. 审批驳回后，返回发起人修改业务资料并重新发起。
6. 历史审批记录必须保留，不能因合同变更或作废而删除。

### 8.3 动态新增其他业务审批

新增其他业务审批前，业务模块必须完成以下接入：

- 提供唯一业务编码。
- 提供业务对象 ID、标题、发起人和详情页路由。
- 定义提交审批前校验。
- 定义审批通过后的业务动作。
- 定义审批驳回后的业务状态。
- 订阅审批作废和审批异常事件。
- 定义消息标题及消息跳转地址。

仅在管理端新增配置但业务模块未完成接入时，不得发起真实审批。

## 9. 审批发起与运行

### 9.1 发起前校验

服务端必须校验：

1. 业务审批配置存在且已启用。
2. 绑定模板存在且已启用。
3. 至少存在一个审批节点。
4. 每个节点的审批策略与人数匹配。
5. 所有具体人员均在职并具备有效账号。
6. 第一个节点不是“上一节点负责人”。
7. 同一业务对象不存在禁止重复发起的进行中审批。
8. 发起人具备该业务对象的操作权限。

任一校验失败时，不生成审批实例。

### 9.2 实例快照

发起时将模板结构和业务审批配置复制为审批实例快照，包括：

- 模板 ID、模板名称。
- 业务编码、业务对象 ID。
- 节点顺序、名称和策略。
- 审批人来源。
- 已能确定的审批人 ID 与姓名快照。
- 发起人、发起时间和业务摘要。

该快照仅用于历史审计，不属于可复用的模板版本。

### 9.3 节点流转

1. 流程按节点顺序串行执行。
2. 仅当前节点可处理，后续节点不得提前操作。
3. 当前节点通过后生成下一节点待办。
4. 最后一个节点通过后，审批实例状态变为“已通过”。
5. 任一当前节点驳回后，审批实例状态变为“已驳回”，不再继续流转。
6. 审批结果与业务状态更新必须在同一服务端事务或可靠事件机制中完成。

## 10. 审批操作

### 10.1 通过

- 单人审批：当前审批人通过后节点完成。
- 或签：任意审批人通过后节点完成。
- 会签：所有审批人通过后节点完成。
- 通过意见选填。

### 10.2 驳回

- 驳回原因必填，建议不少于 5 个字。
- 任意当前审批人驳回后，当前节点及整个审批实例立即结束。
- 流程直接返回发起人，不退回上一审批节点。
- 发起人修改业务资料后重新发起，系统生成新的审批编号和审批实例。
- 新实例使用重新发起时的最新有效配置。

### 10.3 幂等与并发

1. 每次审批提交必须携带审批实例 ID、节点实例 ID 和防重复请求标识。
2. 服务端通过条件更新或行锁保证同一任务只能成功处理一次。
3. 或签节点被一人处理后，其他人的并发操作返回“该节点已处理”。
4. 会签节点任一人驳回后，其他人的后续操作返回“该流程已驳回”。
5. 重复请求不得重复发送消息或重复执行业务回调。

## 11. 配置调整与流程作废

### 11.1 作废触发条件

以下调整保存后，受影响的进行中审批必须作废：

- 模板新增、删除或调整节点顺序。
- 修改节点名称或审批策略。
- 业务审批更换模板。
- 修改任一节点的审批人来源或具体人员。
- 停用业务审批配置。
- 删除业务接入关系。

仅修改模板说明、业务审批名称或业务说明，不作废进行中审批。

### 11.2 作废处理

1. 保存调整前展示受影响的进行中审批数量，并要求二次确认。
2. 确认后，先保存新配置，再批量将受影响实例标记为“已作废”。
3. 关闭所有未完成审批任务和待办。
4. 已完成节点及审批意见保留，不回滚、不删除。
5. 作废原因记录为“审批配置已调整”，并保存操作人和操作时间。
6. 通知发起人原审批已作废，需要重新发起。
7. 新发起流程直接使用最新配置。

## 12. 审批中心

### 12.1 列表视图

| 视图 | 数据范围 |
|---|---|
| 待我审批 | 当前用户仍可操作的 HubX 审批任务 |
| 我发起的 | 当前用户发起的 HubX 审批 |
| 我已处理 | 当前用户已通过或驳回的 HubX 审批 |
| 企业微信审批 | 同步或查询到的企业微信审批，只读 |
| 全部审批 | 当前用户有权查看的全部审批 |

### 12.2 筛选与搜索

- 关键词搜索：审批编号、审批事项、发起人、审批人。
- 审批类型筛选。
- 审批状态筛选。
- 支持分页。

### 12.3 列表字段

- 审批编号。
- 审批事项。
- 审批类型。
- 业务金额，适用时展示。
- 发起人。
- 当前审批人。
- 状态。
- 是否超时。
- 发起时间。
- 操作：详情、审批或查看业务。

### 12.4 审批详情

详情至少展示：

- 审批编号、审批类型、审批事项。
- 关联业务摘要及查看业务入口。
- 发起人、发起时间、最后更新时间。
- 当前状态、当前节点、当前审批人。
- 完整节点顺序。
- 每个节点的策略、审批人、处理状态、处理时间和审批意见。
- 作废原因、作废人和作废时间，适用时展示。

## 13. 状态模型

### 13.1 审批实例状态

| 状态 | 说明 | 是否终态 |
|---|---|---:|
| 审批中 | 流程已发起，存在待处理节点 | 否 |
| 已通过 | 全部节点通过 | 是 |
| 已驳回 | 任一节点驳回 | 是 |
| 已作废 | 因配置调整或业务失效而终止 | 是 |
| 审批异常 | 审批人无法解析或运行异常，待管理员处理 | 否 |

本期不提供发起人主动撤回，因此正式页面不展示“已撤回”状态筛选。

### 13.2 节点状态

- 未开始。
- 待审批。
- 审批中，主要用于会签部分人员已处理。
- 已通过。
- 已驳回。
- 已关闭，主要用于或签、会签中流程提前结束后的剩余任务。
- 已作废。

## 14. 审批编号

建议格式：

| 业务 | 前缀 | 示例 |
|---|---|---|
| 报价审批 | `BJSP` | `BJSP-20260729001` |
| 合同审批 | `HTSP` | `HTSP-20260729001` |
| 其他业务审批 | 管理员配置或系统分配 | `XMLX-20260729001` |

编号由服务端生成，必须保证同一租户内唯一。建议使用业务前缀、日期和当日流水号组合，不得依赖前端自增。

## 15. 消息提醒联动

审批模块只发布标准业务事件，消息提醒模块根据配置决定发送站内信、企业微信应用消息和短信。

### 15.1 事件

- 审批已发起。
- 节点待审批。
- 节点已通过。
- 审批已通过。
- 审批已驳回。
- 审批已作废。
- 审批异常。
- 审批超时。

### 15.2 默认接收人

| 事件 | 默认接收人 |
|---|---|
| 节点待审批 | 当前节点审批人 |
| 审批已通过 | 发起人、业务负责人 |
| 审批已驳回 | 发起人 |
| 审批已作废 | 发起人、当前未处理审批人 |
| 审批异常 | 系统管理员、业务管理员 |
| 审批超时 | 当前审批人；升级时按提醒策略增加接收人 |

### 15.3 渠道

1. 站内信：按消息配置发送。
2. 企业微信应用消息：管理员完成企业微信自建应用配置后启用。
3. 阿里云短信：默认仅用于高优先级或超时升级，并允许在消息策略中配置。
4. 消息必须携带审批编号、事项、当前状态和 HubX 业务跳转地址。
5. 消息发送失败不得回滚已经成功的审批操作，应进入消息重试和发送记录。

## 18. 审计与安全

1. 所有模板、业务配置和审批操作必须记录操作人、时间、变更前后内容。
2. 审批操作日志只允许追加，不允许修改和物理删除。
3. 审批意见按业务数据权限控制，不得通过列表接口泄露。
4. 服务端必须防止越权审批、重复审批和伪造业务对象。
5. 配置调整与批量作废必须在事务中执行并记录影响数量。
6. 涉及金额、合同内容等敏感字段时，日志避免记录完整正文。
7. 企业微信 Secret、短信密钥等凭证不得进入审批记录、前端代码或普通日志。

## 19. 验收标准

### 19.1 模板与业务配置

- 可以新增、编辑、复制审批模板。
- 模板至少包含一个节点。
- 节点支持单人、或签、会签。
- 已被业务使用的模板不能删除或直接停用。
- 不存在独立“审批类型管理”入口。
- 可以直接新增业务审批并绑定模板。
- 报价审批、合同审批默认存在，且合同新建、变更、作废使用同一合同审批配置。
- 单人节点只能选择一位具体人员。
- 或签、会签必须选择至少两位具体人员。
- 第一节点不能选择上一节点负责人。
- 或签、会签不能选择上一节点负责人。

### 19.2 流程运行

- 单人节点一人通过后进入下一节点。
- 或签任意一人通过后进入下一节点，其余任务关闭。
- 会签全部通过后进入下一节点。
- 任意节点驳回后流程结束并返回发起人。
- 发起人重新提交时生成新的审批实例。
- 当前单人节点选择上一节点负责人时：
  - 上一节点为单人，取其实际审批人。
  - 上一节点为或签，取实际通过人。
  - 上一节点为会签，取最后完成通过的人。
- 审批人为空时不允许自动跳过。

### 19.3 配置变更

- 实质调整配置时，保存前提示影响的进行中实例数量。
- 确认后，相关进行中实例全部变为已作废。
- 已完成的节点记录和审批意见仍可查看。
- 发起人收到重新发起提醒。
- 新流程使用最新配置，不继续使用旧配置。

### 19.4 权限与并发

- 非当前审批人无法通过构造请求处理审批。
- 同一审批任务并发提交时只有一次成功。
- 或签节点完成后其他人不能继续审批。
- 已驳回、已通过、已作废流程不能再次处理。
- 消息发送失败不影响审批结果落库。
